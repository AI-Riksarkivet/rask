# open-notifications-coverage — what the bell SHOULD cover, and what it does not

**Status: an audit result, not a plan.** Produced 2026-08-16 by a 12-agent workflow — 8 inventory
agents (one per service), 3 adversarial verify lenses (*does it exist as described* / *is the person
already told* / *is it worth telling*, majority-of-three to survive), 1 synthesis. 90 candidates, 86
survived, 4 refuted.

**Read the count with suspicion.** 86 surviving out of 90 is a 96% pass rate through lenses that were
told to refute, which means the lenses were softer than intended — treat the register as a
*prioritised inventory*, not 86 independent defects. The rows cluster onto roughly six root causes,
which is what §6's sequence actually encodes: a missing `lance.project`, an unpropagated human sub, a
control event never emitted, a name that does not match the FGA object, a discard path that throws
away the subject it is holding, and an audience shape (a *prior* holder, a *role*) that none of the
four sources can model.

**Spot-verified by hand before this was committed** (the two loadbearing claims, not the whole list):
`catalog/core/lineage_emit.py:189` builds `lance_fields = {"operation": ...}` + optional `version` and
**no project** — so `project_id()` returns `None` and `fanout.py:88` skips the watcher loop for every
catalog write in the estate; `ingest/lineage.py:213-215` sets `fields["project"]` and is the working
precedent. Rows below that were NOT hand-verified are the agents' claims — check `file:line` before
acting on one.

**The durable contract distilled from this lives in `.claude/skills/rask-notifications`.** This file
is the work list; the skill is the rule. Fix a producer named here and delete its row; when the
register is empty, delete this file.

## 1. What this plane is for

A notification names a **person** and a **reason**; a feed names an estate. `services/notifications` is an inbox behind a bell — one Dapr `InboxActor` per subject holding claim-check pointers with durable read state (`notifications/models.py:1-15`) — precisely so the badge counts *your* work and not the estate's. That is a targeting problem, not a transport problem: the two ingresses (`lineage.events.v1`, `catalog.control.v1`, plus the 30 s cron reconciler over lineage's durable `GET /events`) carry everything the estate does, and the plane's entire job is to discard all of it except the rows that name a subject under one of four reasons. `NotificationReason` is **stored, never inferred** (`notifications/models.py:43-59`) because a delivery re-check keys on it: "you are the author" and "you watch this project" are different claims about the same run, and a governance row is checked against no object rule at all. The corollary is the whole register below — a state change that names nobody is not under-delivered, it is **undeliverable**, and no amount of subscribing fixes it. The producer is where coverage is decided.

## 3. The four targeting sources, and when each applies

Run the procedure top to bottom. The first match is the source; if none matches, the feature has no audience and needs a producer change before it has a notification.

**Q1 — Does a named person cause the state change, and does it end in a terminal run over a governed object?**
→ **AUTHOR** (`NotificationReason.AUTHOR`, `models.py:54`). Emit a terminal OpenLineage run event (`COMPLETE`/`FAIL`/`ABORT`; `TERMINAL_STATES`, `lineage_events.py:32`) carrying `run.facets.author.sub` = that person's **verified token sub**, and at least one output dataset. `author_subject()` reads `author.sub` and nothing else (`lineage_events.py:118-130`) — never `author.name`, never the standard `ownership` facet, because those are producer-supplied and honouring them would let any producer put a row in a named person's inbox. AUTHOR needs no registry and no opt-in: you may always be told about your own run (`fanout.py:87`).

**Q2 — Is the state change about a project's work, such that people other than the actor should know?**
→ **WATCH** (`models.py:56`). Same event as Q1, plus `run.facets.lance.project` = the tenant id (`project_id()`, `lineage_events.py:143-151`). Watchers are an explicit `project#member`-gated opt-in (`watches.py:40-42, 67-74`); membership gates watching and never implies it. A project-less run reaches its author and no watchers — the safe direction. `fanout.py:88` skips the watcher loop entirely when `project` is `None`, which is why the catalog's missing `lance.project` silently disables WATCH for every catalog write in the estate.

**Q3 — Does the change give a specific person access to something?**
→ **GRANT_ADDED** (`models.py:58`). Publish a `CatalogControlEvent` on `catalog.control.v1` with `action="grant_added"` and `extra["subject"]` = the FGA principal (`user:alice`). `named_subject` strips the `user:` prefix and refuses empty and `*` (`control_events.py:50-72`).

**Q4 — Does the change take access away from a specific person?**
→ **GRANT_REVOKED** (`models.py:59`) — the same envelope with `action="grant_revoked"`. This is the sharper case and the reason the control lane exists: *losing access silently is how someone discovers it by hitting a 403 in the middle of work* (`control_events.py:32-33`). The control lane deliberately runs **no visibility check** — after a revoke the subject can no longer see the object, so a delivery-time check would drop the one event they most need. Being named **is** the targeting (`control_events.py:1-19`).

**No match.** Then say so in the design rather than emitting something adjacent. Four recurring no-match shapes appear in §2: an audience that is a *prior* holder of a thing (annotator leases, review rework, dropped tasks); an audience that is a *role* rather than a person (a project's manager, a project's admin); a fact that only exists at **read** time (flows' composed failures, ingest's `defect` verdict); and a *deletion* whose subjects are enumerable but never enumerated (cascade drops, project deletes). The first two need a fifth source; the third needs a persisted state change; the fourth is mechanical and simply not done.

## 4. THE PRODUCER CONTRACT — how a new feature gets notifications

### 4.1 The LINEAGE lane

Four things must all be true or the row reaches nobody. `notifiable()` (`lineage_events.py:154-203`) returns `None` — "ack it, tell nobody" — on any miss, and the ack is a **success**, so nothing anywhere reports the loss.

1. **Terminal state.** `COMPLETE`, `FAIL` or `ABORT`. `START`/`RUNNING` notify nobody by product decision; `RECONCILED` is excluded on purpose (`lineage_events.py:25-32`).
2. **A VERIFIED `author.sub`.** *A role literal or a display name will silently reach nobody.* This trap already bit the medallion: its movers author with a chart role literal (`data_eng`/`analyst`/`htr`/`ray`, `chart/values.yaml:926-943`), so the pointer addresses an inbox actor literally named `ray` — hidden under FGA, and **written into an unopenable inbox** with FGA off. The same trap by substitution: the annotator's publish uses a service-account bearer (`annotator/projects/lakehouse.py:74-77, 359`), and ingest presents `service-ingest` (`chart/values.yaml:161`). If your emit runs behind a service token, the `author` facet will be **overwritten** with that service's identity by `enforce_author` (`lineage/api/fga_deps.py:103-104`) — carrying the human's sub through your own call graph is the only fix.
3. **`lance.project`**, or WATCH cannot fire. Optional; omitting it costs you every watcher.
4. **At least one output**, whose `name` is the **FGA object id** the delivery gate will check. Delivery runs `can_be_notified` and render re-runs `can_get_metadata` against `table:<object_id>` (`visibility.py:50-60, 137-150`) — so an unqualified dataset name against tenant-qualified grants counts every recipient HIDDEN (`medallion/workflow.py:374`).

```python
# The wire shape `notifiable()` reads. Keys are the OpenLineage aliases (runId/eventType/eventTime).
event = {
    "eventType": "FAIL",                      # (1) TERMINAL. START/RUNNING notify nobody.
    "eventTime": datetime.now(UTC).isoformat(),
    "run": {
        "runId": str(run_uuid),               # graph id; the notification id is `runId@STATE`
        "facets": {
            # (2) VERIFIED sub. `token.sub` from the OIDC bearer — NEVER settings.author,
            #     never a team/role string, never a display name. Both keys, `{name, sub}`,
            #     is what every verifying writer in the estate stamps.
            "author": {"name": token.sub, "sub": token.sub},
            "lance": {
                "operation": "promote",
                "run_id": producer_run_id,    # what YOUR detail door answers to
                "project": project_id,        # (3) WATCH's key. Omit → zero watchers.
            },
            "errorMessage": {"message": reason},
        },
    },
    # (4) ≥1 output, named EXACTLY as the FGA object is named (tenant-qualified if grants are).
    "outputs": [{"namespace": "gold", "name": f"{project_id}-gold$catalog"}],
}

await publish_event(                          # service_kit.dapr_publish
    client, pubsub_name="pubsub", topic_name="lineage.events.v1",
    data=json.dumps(event), data_content_type="application/json",
)
# HTTP alternative: POST /api/v1/lineage on the lineage service. It reaches the durable feed
# only, so notifications sees it via the 30 s cron reconciler — and `enforce_author` REPLACES
# your author facet with the calling token's sub. A service token there = a service inbox.
```

### 4.2 The CONTROL lane

```python
from catalog.core.control_emit import emit_control      # or your service's ControlEmitterDep

await emit_control(                                     # control_emit.py:102-127 — best-effort,
    emitter,                                            #   never raises into a committed mutation
    action="grant_revoked",                             # MUST be in NAMED_ACTIONS
    object_type="project",
    object_id=f"project:{project_id}",
    actor=f"user:{token.sub}",                          # the VERIFIED principal that made the change
    extra={"relation": relation, "subject": user},      # `subject` = WHO this is about, `user:bob`
)                                                       #   — a userset here creates a phantom inbox
```

Call it **after** the FGA/backend mutation and its audit succeed, so a real change is never announced (`control_emit.py:113`). `extra.subject` is the whole targeting: `named_subject` returns `None` for a missing subject, a bare `user:`, and the `*` wildcard (`control_events.py:47, 69-72`), and the event is then filed IGNORED with a `SUCCESS` ack.

**Adding a NEW named action is a three-file change, and all three are load-bearing:**

1. `service_kit/control_events.py:36` — add the member to `ControlAction` so the envelope validates.
2. `notifications/api/control_events.py:34` — add it to `NAMED_ACTIONS`, or the lane files it IGNORED.
3. `notifications/models.py:43-59` — add the matching `NotificationReason` member, **because `as_delivery` constructs `NotificationReason(event.action)`** (`control_events.py:85`) and would otherwise raise on every delivery. The deeper reason is the docstring's: the reason is **stored, not inferred**, because a delivery re-check keys on it — a governance row is checked against no object rule at all, and a reader that could not tell it apart from a run row would have to guess.

### 4.3 The FGA prerequisite

The lineage feed is **governed**. The reconciler reads it with this service's `x-lance-service-identity`, so it sees exactly the rows its service principal is granted — *and a deployment that forgets those grants gets a reconciler that runs cleanly and reconciles nothing* (`notifications/api/reconciler.py:19-21`). There is no retry that helps: the estate's `invokeRetry` policy never retries a 4xx, because a 403's answer will not change. Symmetrically, delivery needs `can_be_notified` and render needs `can_get_metadata` on `table:<output name>` for every recipient — an FGA outage is fail-closed (`RETRY`), never a delivery. A new producer therefore ships **two** grants: notifications' reader grant on the feed, and the recipients' grants on the objects your outputs name.

### 4.4 Testing it with no cluster

The audience rules are exercisable with no sidecar because both seams are **callables, not imports**: `InboxOpener = Callable[[str], TypedActorProxy]` (`fanout.py:37-40`) and `WatcherLookup = Callable[[str], Awaitable[Sequence[str]]]` (`fanout.py:62-64`), with `ChannelPush` the same (`fanout.py:66-69`). `Visibility(client=None, enabled=False)` is the FGA-off value. Drive the whole ingress with `ingest_run_event` (`api/ingest.py:79-121`) — the identical function both lanes run, which is what makes "the same event arriving twice lands one pointer" a property of the projection rather than a coincidence.

```python
from notifications.api.ingest import ingest_run_event, DAPR_SUCCESS
from notifications.api.metrics import Lane
from notifications.api.visibility import Visibility

boxes: dict[str, list[dict]] = {}

class _Inbox:                                  # stands in for the Dapr actor proxy
    def __init__(self, subject): self.subject = subject
    async def deliver(self, payload):
        rows = boxes.setdefault(self.subject, [])
        if any(r["notification_id"] == payload["notification_id"] for r in rows):
            return {"delivered": False}        # idempotent on notification_id
        rows.append(payload)
        return {"delivered": True}

assert await ingest_run_event(
    my_event,                                  # the dict from §4.1
    lane=Lane.BUS,
    visibility=Visibility(client=None, enabled=False),
    watchers=lambda project: _mock[project],   # WatcherLookup
    open_inbox=_Inbox,                         # InboxOpener
) == DAPR_SUCCESS
assert boxes["alice"][0]["reason"] == "author" # AUTHOR fired; a role literal would leave boxes EMPTY
```

Assert on `boxes`, never on the status: an event that names nobody returns `SUCCESS` too. `services/notifications/tests/test_ingress_audience.py` is the worked reference.

## 5. What is deliberately NOT notified

* **Non-terminal states.** `START`/`RUNNING` notify nobody (`lineage_events.py:25-32`). "Your run started" tells the person who clicked start nothing and is noise to everyone else. Consequence, stated plainly: a job that never becomes terminal can only be reported by something that decides to give up on it.
* **Output-less runs.** A dataset-less run names no object, so a pointer would have no honest `object_id` and would pass the visibility test vacuously — disclosing run, author and error to a caller holding no grants. Refused under FGA on **and** off, one rule everywhere (`lineage_events.py:161-167`).
* **Unverified authors.** `author.name` and the standard `ownership` job facet are producer-supplied and are never read for targeting — honouring them would let any producer put a row in a named person's inbox (`lineage_events.py:118-130`). Right for attribution on a board, wrong for addressing an inbox.
* **Wildcard and non-personal principals.** `user:*` strips to a truthy `*` and once delivered a pointer into an inbox actor literally named `*` for every managed-access toggle; filtered at the one place that turns a principal into an address (`control_events.py:36-47`). The rule is "an address must identify a person" — which is exactly the rule a userset subject still violates (§2, catalog).
* **Control actions that name no party.** 22 of the 24 `ControlAction` members are catalog mutations with no named subject; delivering them would recreate the estate-wide feed this plane exists to replace (`control_events.py:16-18`). This is a deliberate exclusion, not an oversight — but it is also why `project_deleted`, `warehouse_deactivated`, `namespace_dropped` and `table_published` reach nobody today, and each of those *does* have an enumerable audience.
* **`RECONCILED`.** Lineage's repair marker for a run whose real terminal event was lost — bookkeeping, not an outcome anyone chose.
* **Synchronous HTTP failures the caller already sees.** A 4xx on the request path is delivered by the response. Four candidates were refuted on this and the adjacent ground — a quality-gate HOLD and an ingest unit-ceiling refusal already reach watchers or the caller, a 24 h run-hour kill is already a terminal FAIL, and a redelivered train trigger's first failure was already a notifiable event. The pattern: **if a terminal event already exists and already carries a real audience, the gap is in that event's addressing, not in a missing notification.**

14. **Give `RayJob` an identity** (`compute/routes.py:29`, `ray-kit/schemas.py`). Nothing in the compute plane can name a person, so job failure, retention deletion and retry-deletion are all unfixable until a submitter rides the submission. *Design.*

16. **Add a fifth targeting source keyed on a task's current or prior holder.** Six annotator gaps (lease expiry, request-changes, drop, adjudication void, skip, publish-saga) collapse to one source; AUTHOR structurally inverts all of them by naming the actor instead of the audience. *Design.*
