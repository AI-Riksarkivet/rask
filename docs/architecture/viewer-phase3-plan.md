# Viewer Phase 3 Implementation Plan

> Authoritative plan for the next viewer backend increment. Companion to [viewer-design.md](./viewer-design.md) — this document is the implementation contract for the four Phase 3 items.

Phase 3 ships four small, additive, backend-only capabilities on the existing FastAPI viewer (`components/services/viewer`): a Ray job-logs endpoint, a Ray Serve health probe, a crash-loop-aware orchestrator cooldown, and a flag-gated OpenTelemetry surface. Every item is read-mostly, schema-free, and stays on the current in-process asyncio orchestrator loop. The bias throughout is the smallest correct change; each section names what was deliberately **not** built.

---

## 1. Goal & scope

**A2 — Ray job logs.** Add one read-only `GET /api/v1/chunks/{chunk_id}/logs` that returns the stdout/stderr of the RayJob currently bound to a chunk, with an optional `?tail=N`. It resolves `current_rayjob_id` from the DB (clean 404 on NULL), calls `ray_client.get_job_logs` via `anyio.to_thread.run_sync`, and trims in Python. It is chunk-keyed to match the existing submit/stop control surface and raises `DomainError` subclasses (404/503) like its neighbors, never `HTTPException`. No streaming, no schema, no frontend.

**A3 — Ray Serve health.** Add a sibling `GET /api/v1/ray/serve` that reports whether the two Serve apps (`transcribe`, `htrflow`) are up and at full replica strength — per-app, per-deployment — by GETting the dashboard's `/api/serve/applications/` over the shared `app.state.http`. It follows the same `try/except httpx.HTTPError → ok=False` shape as `ray_dashboard.cluster_status()`: never 500, returns `ok=False`/`status=not_ok` on outage, reads replica targets live (no hardcoded `3`), and adds no deps, no `ray.init`, no schema, no new Settings field. (It is **not** byte-identical to `cluster_status` — that read passes no per-request timeout; A3 passes a literal `timeout=` on its one GET, see A3 design.)

**A4 — Smart cooldown.** Replace the flat 600 s per-job cooldown (`derive.py`) with a per-**chunk**, crash-loop-aware policy: count consecutive failures per chunk from Ray history, apply a plain deterministic `backoff = min(base * 2**(n-1), cap)` (no jitter — see below for why it is deliberately not built), and quarantine (stop auto-resubmission) once `n >= N`. A tiny self-decaying in-memory `dict[int, ChunkFailState]` on `app.state` pins the count so a Ray-GCS/head-node wipe within one uptime can't silently un-quarantine a looping chunk. No schema change, no migration, no new Batch column; manual `POST /chunks/{id}/submit` stays a working override.

**OTel — traces + metrics.** Add a minimal, flag-gated OpenTelemetry signal set: programmatic SDK bootstrap in `make_lifespan` (true no-op when `RASK_OTEL_ENABLED` is unset), FastAPI request spans (health route excluded), free child CLIENT spans from httpx + SQLAlchemy auto-instrumentation, stdlib-logging→OTel correlation via env, and a small fixed set of golden-signal manual instruments on the orchestrator (tick span + tick-duration histogram + tick-error counter + submissions counter + a per-failing-job counter incremented at the inner job grouping). Zero overhead when off.

## 2. Explicitly OUT OF SCOPE

These are the load-bearing non-decisions. They make review fast and keep the diff honest.

- **Orchestration stays on the in-process asyncio loop.** No `nats-py`, no JetStream, no broker, no queue, no event bus this phase. NATS JetStream remains the *documented eventual target* (see CLAUDE.md orchestrator note); every new function (`chunk_logs`, `serve_status`, `derive_state`, the orchestrator tick span) is written transport-agnostic so it ports to a future consumer with no restructuring. **One-line migration note:** when the loop becomes a JetStream consumer, the A4 tracker dict becomes consumer-side durable state and the `orchestrator tick` span is the `propagate.inject`/`extract` seam — neither requires touching the Phase 3 logic.
- **No schema change / no migration / no new Batch columns.** Phase 2 schema work is paused. A4 cooldown + quarantine state is **in-memory / derived only** (Ray history + the `app.state` dict). Consequence accepted and documented: a stopped chunk's last logs (A2) are not retrievable, and the A4 tracker is lost on viewer restart.
- **No SvelteKit / frontend work.** All four items are backend-only. Endpoints return JSON (or `application/problem+json` on `DomainError`). A4's quarantine/backoff surface only as additive JSON fields on the existing `GET /orchestrator/state`. Any SPA adaptation is a later, out-of-scope concern.
- **Bounded OTel surface.** Flag-gated, default off. Exactly: auto FastAPI/httpx/SQLAlchemy instrumentation + four manual orchestrator instruments. No `GET /metrics`/Prometheus endpoint, no per-Ray-stage or per-batch spans, no custom `http.server.*` metric (FastAPIInstrumentor already emits it), no gauges, no SDK-side sampling, no structlog, no launcher (`opentelemetry-instrument`)/`opentelemetry-bootstrap`. Protocol/service-name/endpoint stay on standard `OTEL_*` env, not re-aliased under `RASK_`.

## 3. Per-item design

### 3.A2 — Ray job logs

**Decision (and why).** Chunk-keyed one-shot fetch: `GET /api/v1/chunks/{chunk_id}/logs` backed by `submission_service.chunk_logs()`, which resolves `current_rayjob_id` from the DB, calls `ray_client.get_job_logs` via `to_thread.run_sync`, and trims to `tail` in Python. Returns a Pydantic v2 `ChunkLogs`.
- Chosen over a **submission_id-keyed route in `ray.py`** because the whole chunk control surface (`submit`/`stop`) is chunk-keyed — operators think in `chunk_id`, so this needs no prior `/ray/jobs` lookup. Build one or the other, not both.
- Chosen over **SSE/websocket live tail** (`tail_job_logs` + `StreamingResponse`) — that is over-engineering for this phase (second aiohttp websocket lifecycle, disconnect handling) and only helps while a job is live; the dashboard iframe / a manual re-GET covers that.
- Because `logs` lives beside `submit`/`stop`, which **raise** `DomainError`s, `chunk_logs` raises `ServiceUnavailableError`/`NotFoundError` — *not* the `ok=False` payload style used by `/ray/*` reads. The DB resolver owns the clean 404 (NULL `current_rayjob_id` → `NotFoundError` before any Ray call). Any `RAY_TRANSIENT_ERRORS` from `get_job_logs` map to `ServiceUnavailableError`; we deliberately do **not** string-parse `'404'` out of Ray's `RuntimeError`.

**API / signatures.**
- `GET /api/v1/chunks/{chunk_id}/logs?tail={int|None}` → `ChunkLogs` (200). `503` when `ray_client is None` or `get_job_logs` hits `RAY_TRANSIENT_ERRORS`; `404` when the chunk has no `current_rayjob_id`; `422` when `tail <= 0` (`Query(default=None, gt=0)`).
- `viewer.schemas.chunk.ChunkLogs(BaseModel)`: `chunk_id: int`, `submission_id: str`, `logs: str`, `line_count: int`, `truncated: bool`.
- `viewer.services.submission.chunk_logs(session, ray_client, *, chunk_id: int, tail: int | None = None) -> ChunkLogs`.
- `viewer.repositories.batch.current_rayjob_id(session, chunk_id: int) -> str | None` — new shared resolver; `stop_chunk`'s inline select is refactored to call it.

**Data flow.** Route guards `ray_client is None → ServiceUnavailableError('Ray dashboard unreachable')` (mirrors submit/stop boot-offline guard), then delegates. `chunk_logs`: (1) `submission_id = await batch_repo.current_rayjob_id(...)`; `None → NotFoundError(f'no running job for chunk {chunk_id}')`. (2) `logs = await to_thread.run_sync(ray_client.get_job_logs, submission_id)` wrapped in `try/except RAY_TRANSIENT_ERRORS → ServiceUnavailableError(...) from exc`. (3) `lines = logs.splitlines()`; if `tail is not None and tail < len(lines)`: take `lines[-tail:]`, `truncated=True`, `line_count=tail`; else full body, `truncated=False`, `line_count=len(lines)`. Read-only; no DB writes; same select on sqlite/postgres.

**Edge cases.** Never-submitted or stopped chunk → resolver `None` → 404 by design (logs-after-stop not retrievable without a schema change). Ray offline at boot → `ray_client is None` → 503 at the guard. Pruned-but-still-tagged job → `get_job_logs` raises `RuntimeError` (in `RAY_TRANSIENT_ERRORS`) → 503; the genuinely-offline and pruned-job cases are indistinguishable by exception type and both resolve to 503 (accepted, vs brittle string-parsing). `tail=0`/negative → 422. `tail >= total` → full log, `truncated=False`. Empty log → `logs=''`, `line_count=0`, `truncated=False`, 200 (job exists). No default cap — `?tail` is the only bound.

**File-by-file.**
- `…/viewer/schemas/chunk.py` — add `ChunkLogs(BaseModel)` next to `SubmitResult`/`StopResult`.
- `…/viewer/repositories/batch.py` — add `current_rayjob_id(...)` (`select(Batch.current_rayjob_id).where(col(Batch.chunk_id) == chunk_id).limit(1)`).
- `…/viewer/services/submission.py` — add `chunk_logs(...)`; refactor `stop_chunk`'s inline select to the shared resolver; **in-scope cleanup**: upgrade `stop_chunk`'s bare `raise ValueError('no running job…')` (currently 500) to `NotFoundError` (same pattern the new endpoint uses).
- `…/viewer/api/v1/endpoints/chunks.py` — add `get_chunk_logs(...)` with the `ray_client is None` guard; import `ChunkLogs` and `Query`.
- `…/viewer/tests/test_chunk_logs_endpoint.py` — new module (below).

**Test plan.** Reuses the seeded-sqlite + `create_app` fixtures from `test_chunk_submit_endpoint.py`; overrides `get_ray_client` with a `FakeRayClient` exposing `get_job_logs`.
- `test_logs_for_chunk_with_no_job_returns_404` — NULL `current_rayjob_id` → 404 `application/problem+json`, `status==404`, `title=='Not Found'`, `'chunk'` in detail (fake `get_job_logs` not called).
- `test_logs_returns_full_log_200` — seeded `current_rayjob_id`, fake returns `'line1\nline2\nline3'` → 200, `line_count==3`, `truncated is False`.
- `test_logs_tail_trims_and_sets_truncated` — `?tail=2` → `'line2\nline3'`, `line_count==2`, `truncated is True`.
- `test_logs_tail_geq_total_not_truncated` — `?tail=10` on 3 lines → full, `truncated is False`.
- `test_logs_tail_zero_returns_422`.
- `test_logs_ray_offline_returns_503` — boot with `RAY_DASHBOARD_URL=http://127.0.0.1:1`, chunk has an id → guard fires → 503 `'Ray dashboard unreachable'`.
- `test_logs_sdk_runtimeerror_returns_503` — fake `get_job_logs` raises `RuntimeError('job not found')` → 503, detail contains the submission_id.
- `test_logs_empty_log_returns_200_not_404` — `''` → 200, `line_count==0`.
- Unit test of `repositories.batch.current_rayjob_id` against seeded sqlite (id present / NULL).

### 3.A3 — Ray Serve health

**Decision (and why).** New sibling endpoint `GET /api/v1/ray/serve` backed by `ray_dashboard.serve_status(http, dashboard_url)`, which GETs `{dashboard_url}/api/serve/applications/` via the existing `app.state.http`, parses the `ServeInstanceDetails` JSON dict into new Pydantic v2 value objects, maps Serve's enums to a two-state `ServeHealth` StrEnum `{ok, not_ok}` per app, and returns a flat `ServeStatusPayload` directly so FastAPI emits 200 even on outage (`ok=False`).
- The task is "are the two Serve apps up at full strength" — a localhost health probe, not a monitoring dashboard. So the roll-up is intentionally coarse: **two states per app** (`ok` iff the app is `RUNNING` and every deployment is `HEALTHY` with `running==target`, else `not_ok`), `running` read from the replica-state **count dict** (`replica_states`) exactly as `deploy_serve.py cmd_status` already does — **no per-replica objects**, **no `degraded` middle state**, **no `_worst()` reducer**. `payload.ok` is simply `all(app.status == ok for required apps)`. A `degraded` middle state would be one additive enum value + one branch if the (out-of-scope) SPA ever wants it; nothing consumes it this phase, so it is **deliberately not built**.
- Chosen over **folding into `/ray/health`** — `RayHealth` is deliberately Jobs-API-liveness-only; mixing a thread-offloaded SDK probe with an httpx GET muddies error semantics.
- Chosen over **`ray.serve.status()` via `to_thread`** — that needs `ray.init()`/a Serve client in the web process (heavy, fragile, against the thin-wrapper module docstring).
- The REST path is the same internal-dashboard contract `serve status`/the Serve CLI use and the same risk class already accepted for `cluster_status()` (`/api/cluster_status`).

**API / signatures.**
- `GET /api/v1/ray/serve` → `ServeStatusPayload` (always 200; `ok=False` + `status=not_ok` on outage). `ray.router` already has prefix `/ray` and is already included — **no `router.py` edit**.
- `async def ray_dashboard.serve_status(http: httpx.AsyncClient, dashboard_url: str) -> ServeStatusPayload` (same signature as `cluster_status`).
- Endpoint: `async def ray_serve(http: HttpDep, settings: SettingsDep) -> ServeStatusPayload: return await ray_dashboard.serve_status(http, settings.ray_dashboard_url)`.
- New `schemas/ray.py` models: `ServeHealth(StrEnum)` (two values: `OK = 'ok'`, `NOT_OK = 'not_ok'`); `ServeDeployment`, `ServeApplication`, `ServeStatusPayload` — a **flat** shape `ServeStatusPayload{ok: bool, status: ServeHealth, apps: list[ServeApplication], error: str | None}`, each `ServeApplication{name, status: ServeHealth, message, deployments: list[ServeDeployment]}`, each `ServeDeployment{name, status: ServeHealth, running: int, target: int}`. All v2 BaseModel built from the JSON dict — do **not** import Ray's V1 `serve.schema` classes, and **no `ServeReplica` per-replica object**.

**Data flow.** `ray_serve()` resolves `HttpDep` + `SettingsDep` → `serve_status`: one `await http.get(f'{dashboard_url}{_SERVE_APPLICATIONS_PATH}', timeout=_SERVE_HEALTH_TIMEOUT)` then `raise_for_status()`. `_SERVE_HEALTH_TIMEOUT = 3.0` is a **module-level constant** in `ray_dashboard.py` (mirrors the existing `_ERROR_MSG_MAX_LEN`/`_RAY_KEY_*` constants) — short so a wedged controller fails fast; **not** a Settings field / `RASK_*` env var (no operator-tunable config surface for one GET). On `httpx.HTTPError` → `ServeStatusPayload(ok=False, status=NOT_OK, error=…[:_ERROR_MSG_MAX_LEN])` (same truncation/`ok=False` convention as `cluster_status`). On success: for each **required** app name in `{transcribe, htrflow}`: absent → `ServeApplication(name=…, status=NOT_OK, message='not deployed', deployments=[])`; present → read app status/message + each deployment's `DeploymentStatus` and its `replica_states` **count dict** (sum of counts where the state key is `RUNNING`) vs `target_num_replicas` read **live** (never hardcode 3). Roll-up (two flat rules, no reducer):
- deployment `status = OK` iff its `DeploymentStatus == 'HEALTHY'` and `running == target`, else `NOT_OK`.
- app `status = OK` iff its `ApplicationStatus == 'RUNNING'` and every deployment is `OK`, else `NOT_OK`.
- `payload.status = OK` iff every required app is `OK`, else `NOT_OK`; `payload.ok = (payload.status == OK)`.

**Edge cases.** Dashboard unreachable → `ok=False`/`not_ok` + error (offline-clean like `/ray/cluster`). Wedged controller → bounded by the 3.0 s `_SERVE_HEALTH_TIMEOUT` constant, *not* the shared 15 s `http_timeout`. Required app missing → `not_ok` (both apps gate as required for v1; htrflow-as-informational is a one-line future constant flag, deliberately not built). `0/N` running while `DeploymentStatus=='HEALTHY'` → `not_ok` (HEALTHY-but-not-serving, since `running != target`). Partial replicas (`1/3`) → `not_ok`. Rescale (`target=2`, `2/2`) → `ok` (live target). Unknown app/deployment status string → `not_ok` (anything that isn't the exact healthy string), no `KeyError` (reads strings off the dict with `.get()` defaults). Extra third app → reported in `apps` for visibility but only the two required apps gate `payload.ok`. Missing `applications` key → `body.get('applications') or {}` → both required apps "not deployed" → `not_ok`, still 200.

**File-by-file.**
- `…/viewer/schemas/ray.py` — add `from enum import StrEnum`; the two-value `ServeHealth` enum and the three BaseModels (`ServeDeployment`, `ServeApplication`, `ServeStatusPayload`). **Convention deviation, called out as a conscious choice:** every other viewer StrEnum (`HtrStatus`, `ManifestStatus`, `BrowseTier`, `RayStage`, `TaskState`) lives in `models/enums.py` whose docstring is "Viewer-defined StrEnums"; only `Slot` lives elsewhere (in `pipelines.py`, for a domain-grouping reason). `ServeHealth` is placed here, beside the other `/ray/*` shapes, to keep all Serve response types in one module — a deliberate deviation from the established StrEnum home, not silent drift. (If a reviewer prefers, moving it to `models/enums.py` is a one-line change with no behavioural effect.)
- `…/viewer/services/ray_dashboard.py` — extend the `from viewer.schemas.ray import …` line; add module-level constants `_SERVE_APPLICATIONS_PATH = '/api/serve/applications/'`, `_REQUIRED_SERVE_APPS = ('transcribe', 'htrflow')` (names only — duplicated locally rather than importing `deploy_serve.APPS` into the service layer), `_SERVE_REPLICA_RUNNING = 'RUNNING'`, `_SERVE_HEALTH_TIMEOUT = 3.0`; one small `async def serve_status(...)` that parses the dict inline (two `OK`/`NOT_OK` rules above — **no `_deployment_health`/`_app_health`/`_worst` helper triplet**) and reuses `cluster_status`'s `except httpx.HTTPError` branch shape.
- `…/viewer/api/v1/endpoints/ray.py` — add `ServeStatusPayload` import + the `@router.get('/serve')` route after `ray_cluster`. No `HTTPException`/`DomainError` — Serve-down is 200 + `ok=False`.
- `…/viewer/core/config.py` — **no change** (the probe timeout is a module-level constant in `ray_dashboard.py`, not a Settings field).
- `…/viewer/tests/test_ray_serve_health.py` — new module.
- `…/viewer/api/v1/router.py` — **no change** (route rides the existing `/ray` include).

**Test plan.** Offline endpoint smoke (boot with `RAY_DASHBOARD_URL=http://127.0.0.1:1`, `TestClient`, assert `200` + `ok False` + `status=='not_ok'` + JSON not problem+json) plus direct `serve_status` calls with a stub `http` whose `.get` returns a hand-built `ServeInstanceDetails` dict: all-healthy `3/3` → `ok`, partial-replicas `1/3` → `not_ok`, zero-replicas → `not_ok`, required-app-missing → `not_ok`, deploy-failed → `not_ok`, rescaled `target=2`/`2/2` → `ok` (no false negative on live target), unknown-status-string → `not_ok`. Run via `uv run pytest …/tests/test_ray_serve_health.py`; `uvx ty check` + `make check` clean, no suppressions.

### 3.A4 — Smart cooldown

**Decision (and why).** **Option B**: Ray-history derivation as the primary signal **plus** a small in-process `dict[int, ChunkFailState]` on `app.state.chunk_fail_tracker`, threaded into `derive_state` as an explicit parameter.
- Rejected **pure derivation (Option A)**: Ray 2.55.1 GCS `internal_kv` is in-memory by default with no external Redis here, so a head-node restart — the exact crash A4 guards — wipes job history and silently forgets quarantine + resets backoff mid-uptime. The dict closes that gap at the cost of one int + two fields per failing chunk, with self-decay so it can't grow unbounded.
- Rejected **bare-set quarantine (Option C)**: splits one feature across two mental models; a GCS wipe would strand a chunk quarantined with no visible failing job.
- The dict is the natural seam that later becomes NATS-consumer state. Threading it as a parameter (like `http`/`client`/`session` already are) keeps `derive_state` pure and testable via the existing `_FakeRayClient.jobs` surface — derive never reaches into `app.state`. Backoff/quarantine knobs become Settings, replacing the module-level `FAIL_COOLDOWN_SECS`. **No jitter** — `expires_in_secs` is the plain deterministic `min(base * 2**(n-1), cap) - elapsed`, which is already correct, trivially stable across the per-tick and per-GET recomputes, and easy to assert exactly in tests. Jitter exists to de-synchronize *many* clients retrying at once; this is one in-process loop submitting a handful of chunks per tick with no thundering-herd it actually causes, so jitter is **deliberately not built** (and a seeded-RNG-for-stability scheme would be pure machinery — `hash()` isn't even reproducible across restarts). **No new endpoint** — quarantine surfaces in `GET /orchestrator/state`, and the existing manual submit is the un-quarantine affordance.

**API / signatures.**
- `GET /api/v1/orchestrator/state` → `OrchestratorState` (**path unchanged**; response extended): `+ quarantined: list[int]`, `+ backoff_base_secs/backoff_max_secs/quarantine_after` (read-only, surfaced from settings), existing `cooldown_secs` kept for back-compat (`= backoff_base_secs`).
- `Cooldown` extended: `+ consecutive_failures: int = 0`, `+ quarantined: bool = False`. **Now one `Cooldown` per chunk** (newest failed job) instead of one per failed job.
- `derive_state(*, http, client, dashboard_url, session, tracker: ChunkFailTracker, base_secs: int, max_secs: int, quarantine_after: int) -> OrchestratorState`.
- New `ChunkFailState(BaseModel)`: `chunk_id: int`, `consecutive: int`, `last_end_ms: int | None`, `quarantined: bool`; `ChunkFailTracker = dict[int, ChunkFailState]` (type alias) on `app.state.chunk_fail_tracker`, mutated only inside derive's merge step.
- **No new HTTP endpoint.** `POST /chunks/{id}/submit` and `/stop` unchanged — manual submit remains the override (its path has no cooldown check).

**Data flow.** Per tick **and** per `GET /orchestrator/state`: `derive_state` fetches jobs via the single existing `ray_dashboard.list_jobs` round-trip (no new Ray calls). New `_per_chunk_fail_states(jobs)`: group all jobs by `_chunk_id_of` (collapsing the timestamp-suffixed submission_ids of one chunk), sort each group by `(end_time or start_time)` asc, count the consecutive FAILED **tail** from the newest job backward; any newer `SUCCEEDED/STOPPED/RUNNING/PENDING` resets to 0. Produce `derived_n[chunk_id]` + the newest failed `RayJob` per chunk (for `error_type`/`message`/`driver_exit_code`/`end_time`). **Merge** with the tracker: `tracker[cid].consecutive = max(derived_n, tracker_prev)` on a fresh failure (history-authoritative when richer, dict-pinned when history wiped); **decay** = drop entries whose chunk now has a SUCCEEDED/RUNNING job *or* whose newest job end is older than `backoff_max_secs` (self-prunes, bounded by failing-chunk count). Per failing chunk: `backoff = min(base * 2**(n-1), cap)`; `expires_in_secs = max(0, int(backoff - elapsed_since_newest_fail))` (no jitter); `quarantined = n >= quarantine_after`. Build one `Cooldown` per failing chunk (in-window or quarantined). **Lane gating unchanged in shape**: `cooldown_pf`/`cooldown_htr` now also include quarantined chunk_ids; `eligible_* = ready − in-flight − (cooldown ∪ quarantine)`. `loop.tick` submits `eligible_*` as today, so quarantined/cooled chunks are simply never eligible → the auto-loop stops hammering. Manual submit bypasses all of this; a later SUCCEEDED/STOPPED job → next derive resets the streak → decay drops the entry → quarantine auto-clears.

**Edge cases.** `end_time is None` mid-teardown → order the group by `start_time` fallback so the None-end failure still participates; for the elapsed calc, a None end is treated as `elapsed=0` → full backoff (do **not** silently drop the chunk — that is the bug the per-chunk rewrite fixes). STOPPED (manual) and SUCCEEDED **reset** the streak; only FAILED increments (`JobStatus = {PENDING, RUNNING, STOPPED, SUCCEEDED, FAILED}`). No jitter is computed, so there is no flicker to avoid — `expires_in_secs` for a given `(chunk, n, now)` is exact. GCS/head-node restart → `derived_n` drops to 0 but the pinned count keeps quarantine alive (the central guarded scenario). Viewer restart loses the tracker entirely — **accepted, documented as transitional**; Ray history re-seeds backoff next tick in the common case. A looping chunk now emits exactly one `Cooldown` (was one per failed job), so the state payload no longer balloons. Unknown/out-of-band submission_id → `_chunk_id_of` None → excluded. Manual submit during quarantine structurally allowed — do **not** add a check. **Two pipelines on one chunk (the load-bearing safety path):** the in-flight guard and lane gating are the property that keeps a quarantined chunk from being resubmitted on *either* lane. `_slot_for(newest failed sid)` assigns the `Cooldown` to the lane that failed, and the quarantine set is unioned into **both** `cooldown_pf` and `cooldown_htr` so the chunk is excluded from `eligible_prefetch` **and** `eligible_htr` (covered by a dedicated test, see test plan). No blocking IO added — all new logic is CPU arithmetic over the already-fetched jobs list.

**File-by-file.**
- `…/viewer/schemas/orchestrator.py` — add `ChunkFailState` + `ChunkFailTracker` alias; extend `Cooldown` (`consecutive_failures`, `quarantined`); extend `OrchestratorState` (`quarantined`, `backoff_base_secs`, `backoff_max_secs`, `quarantine_after`; keep `cooldown_secs`).
- `…/viewer/services/orchestrator/derive.py` — remove `FAIL_COOLDOWN_SECS`; add the reset-set frozenset, `_per_chunk_fail_states`, `_backoff_secs`; rewrite the cooldown block to merge/decay the passed-in tracker and emit one `Cooldown` per failing chunk; change `derive_state` signature; add quarantined ids to lane gating; return the extended `OrchestratorState`. Docstring cites the resilience principle it implements: capped exponential backoff (no jitter — single-loop, no thundering herd).
- `…/viewer/core/config.py` — add `fail_cooldown_base_secs`, `fail_cooldown_max_secs`, `fail_quarantine_after` (see config table).
- `…/viewer/core/lifespan.py` — `app.state.chunk_fail_tracker = {}`; pass into `create_orchestrator_task → run_orchestrator_loop`. No teardown (plain dict).
- `…/viewer/services/orchestrator/loop.py` — thread `tracker` + the three knobs into `tick`/`run_loop` and the `derive_state(...)` call; submission logic unchanged (it already only submits `state.*.eligible`).
- `…/viewer/api/v1/endpoints/orchestrator.py` — in `orchestrator_state`, read `request.app.state.chunk_fail_tracker` and pass it + the three settings into `derive_state`. No new route.

### 3.OTel — traces + metrics

**Decision (and why).** **Option 1** — programmatic SDK bootstrap inside `make_lifespan`, gated by `Settings.otel_enabled` (default False) + a resolvable OTLP endpoint.
- Over **Option 2 (launcher `opentelemetry-instrument`)**: the launcher forces a Makefile/prod-launch change and makes a plain `uvicorn`/`pytest` run inconsistent; health-exclusion would leak to `OTEL_PYTHON_FASTAPI_EXCLUDED_URLS` env; `opentelemetry-bootstrap -a install` pulls unvetted instrumentation. Conventions prefer an app-owned Settings gate. The launcher's only real win (atexit flush) is cheaply replaced by the lifespan `finally`.
- Over **Option 3 (maximal)**: rejected by the owner as over-engineering — per-stage/per-batch spans blow the span budget and duplicate auto-instrumentation; a custom `http.server.*` metric conflicts with FastAPIInstrumentor's series.
- Chosen path adds exactly: (a) auto request spans (health excluded), (b) free child CLIENT spans from httpx + SQLAlchemy, (c) stdlib-logging→OTel via env, (d) four manual orchestrator instruments. Flag off → no providers, no instrumentation, global `get_tracer`/`get_meter` return no-ops → manual call sites cost nothing.

**API / signatures.**
- `GET /api/v1/health` — unchanged; **excluded** from request spans (probe noise).
- `GET /api/v1/orchestrator/state`, `POST /orchestrator/start|stop`, `POST /chunks/{id}/submit|stop` — unchanged; submit increments the submissions counter.
- **No** new endpoint, **no** `GET /metrics`.
- `viewer/core/telemetry.py` (new): `setup_telemetry(app, settings) -> object | None` (None when disabled), `shutdown_telemetry(holder) -> None`.
- `viewer/services/orchestrator/metrics.py` (new): module-level `meter = metrics.get_meter(__name__)` + `ORCHESTRATOR_TICK_DURATION` (histogram, `unit='s'`), `ORCHESTRATOR_TICK_ERRORS` / `ORCHESTRATOR_SUBMISSIONS` / `ORCHESTRATOR_JOB_FAILURES` (counters). Cheap no-ops until a `MeterProvider` is set.

**Data flow.** Boot: in `lifespan`, **after** `app.state.db_engine`/`db_sessionmaker` are built (SQLAlchemyInstrumentor needs `.sync_engine`) and before the orchestrator task, `app.state.telemetry = setup_telemetry(app, settings)`. Disabled or no endpoint → returns None, builds/instruments nothing. Enabled → `TracerProvider(BatchSpanProcessor(OTLPSpanExporter))` + `MeterProvider(PeriodicExportingMetricReader(OTLPMetricExporter))`; `set_tracer_provider`/`set_meter_provider` (once); `FastAPIInstrumentor.instrument_app(app, excluded_urls=f'{settings.api_prefix}/health', tracer_provider=…, meter_provider=…)`; `HTTPXClientInstrumentor().instrument()`; `SQLAlchemyInstrumentor().instrument(engine=app.state.db_engine.sync_engine)`; logging via `OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED=true`.
- **Request path (auto):** inbound HTTP → FastAPI SERVER span (health excluded) → httpx CLIENT spans (Ray dashboard) + SQLAlchemy CLIENT spans nest underneath.
- **Orchestrator path (manual):** `run_loop` tick → `tracer.start_as_current_span('orchestrator tick')`; time `tick()`; record `ORCHESTRATOR_TICK_DURATION.record(elapsed_s)` in `finally`. In `run_loop`'s `except Exception`: keep `log.exception`, add `span.set_status(StatusCode.ERROR, f'{type(exc).__name__}: {exc}')` + `ORCHESTRATOR_TICK_ERRORS.add(1)`. Ray-transient (`state.ok False` early return / `RAY_TRANSIENT_ERRORS` caught) stays **UNSET**, not ERROR. `submit_chunk` success → `ORCHESTRATOR_SUBMISSIONS.add(1, {'pipeline': spec.name, 'slot': spec.slot.value})`.
- **Job-failure counter placement (reconciled with A4's per-chunk rewrite):** after A4 the outer cooldown loop iterates **per chunk**, so incrementing there would count failing *chunks*, not failing *jobs*. The counter must therefore be incremented at the **inner job grouping** inside `_per_chunk_fail_states`, where individual FAILED jobs are still visible: `ORCHESTRATOR_JOB_FAILURES.add(1, {'slot': _slot_for(sid).value})` once per FAILED `RayJob` seen in the consecutive-failure tail. This keeps the metric a per-job count (its intended meaning) and keeps the documented "mild over-count across ticks" tradeoff accurate (a FAILED job in a chunk's tail is re-counted each tick until it ages out / the streak resets; exact-once would need a seen-set we deliberately omit).
- **Shutdown:** lifespan `finally`, beside `http.aclose`/`db_engine.dispose`: `shutdown_telemetry(app.state.telemetry)` → `tp.shutdown()` + `mp.shutdown()` (guarded for None).
- **NATS seam (documented, not built):** the `orchestrator tick` span is where `propagate.inject`/`extract` later moves.

**Edge cases.** Hard no-op when disabled (default; existing tests untouched). Enabled but no endpoint → treat as disabled (fail closed, no half-init, no connection-error spam). `excluded_urls` derived from `settings.api_prefix` (not hardcoded). SQLAlchemyInstrumentor uses the **sync** engine; backend-agnostic across sqlite/asyncpg with no driver branch. **OTel context does not cross into `anyio.to_thread` worker threads** — so any span around the Ray SDK calls must open on the async side (where the tick span already sits); do not open spans inside the threaded fn. Tick span ERROR only on the final caught Exception, never on transient Ray-down. Metric attributes bounded only — `pipeline` + `Slot`; `chunk_id` is unbounded → span/log only, never a metric attribute. Job-failure counter: incremented per FAILED job in the consecutive-failure tail inside `_per_chunk_fail_states` (NOT in the per-chunk cooldown loop, which would count chunks not jobs after the A4 rewrite); accepts mild over-count across ticks while a failure stays in a chunk's tail, exact-once would need a seen-set we omit. Double-instrumentation guard: instrumentors are process-global; only ever enabled in a single-app process — tests keep it False, and any enabled-path test must `uninstrument` in teardown (no global guard cruft in prod). Error contract (DomainError → problem+json) untouched; the existing 5xx `log.exception` auto-correlates once LoggingInstrumentor is on.

## 6. Recommended sequencing

Ordered to land quick independent wins first, then the items that share plumbing, then the one cross-cutting change that touches the most files.

1. **A3 — Serve health (M1, independent quick win).** Pure additive httpx read; touches only `schemas/ray.py`, `ray_dashboard.py`, `endpoints/ray.py` (no Settings field, no router edit — the probe timeout is a module-level constant); follows the same offline-`ok=False` shape as the already-merged `cluster_status`. Smallest blast radius, zero coupling to the others. Do first to validate the offline-`ok=False` test pattern fresh.
2. **A2 — Ray job logs (M1, independent quick win).** Also additive; touches `schemas/chunk.py`, `repositories/batch.py`, `submission.py`, `endpoints/chunks.py`. Its only cross-cut is the small `stop_chunk` resolver/`ValueError→NotFoundError` cleanup — confined to `submission.py`. Independent of A3; can land in parallel.
3. **A4 — Smart cooldown (M2, shares orchestrator plumbing).** Larger and the only state-bearing change. Touches `schemas/orchestrator.py`, `derive.py`, `loop.py`, `lifespan.py`, `endpoints/orchestrator.py`, `config.py`, **plus the `_FakeJobDetails` extension in `tests/test_pipelines.py`** (must land with A4 so its unit tests are writable). The `derive_state` signature grows by four params, so **every caller must change in the same pass** (consistency rule). A4 and OTel both touch `submission.py`/`derive.py`, but A4's edits are disjoint from OTel's (A4 touches none of `submission.py` except the OTel counter, which lands later), so there is no real conflict — sequencing A4 before OTel is confirmed fine. Land after A2/A3 so the orchestrator files are touched only once for logic, then once more for OTel.
4. **OTel (M3, cross-cutting, last).** Depends on the orchestrator code being stable (it instruments `loop.py`/`derive.py`/`submission.py` and the lifespan). **The one genuine ordering coupling:** the `ORCHESTRATOR_JOB_FAILURES` counter must be placed inside A4's inner `_per_chunk_fail_states` grouping (per failed job), not the per-chunk cooldown loop — so the A4 loop shape must be settled before OTel wires the counter (see the OTel data-flow reconciliation). Doing OTel last means the manual instruments wrap final A4 code rather than chasing a moving target, and the new dep + `uv sync` + `ty`-clean-without-suppressions verification happens once at the end. Off by default, so it can't destabilize the M1/M2 test suites.

Dependencies in short: M1 (A2, A3) are independent of everything and of each other; A4 depends on no other item but shares files with OTel; OTel depends on A4 being settled. Each milestone ends green under `make check` with no `# type: ignore`/`# ty: ignore`.

## 8. Risks & open questions

**A2 — Ray job logs (low).** The one gotcha: Ray funnels every non-200 (including a 404 for a pruned job) through a bare `RuntimeError`, which is also in `RAY_TRANSIENT_ERRORS` — so a pruned-but-still-tagged job reports 503 "unavailable" rather than 404 "gone". Mitigated by letting the DB NULL-check own the common 404; we accept 503 for the rare pruned-id case over brittle string-parsing. Secondary: `get_job_logs` returns the whole log, so a chatty job yields a large JSON body — bounded by `?tail`, acceptable for a localhost/trusted-network tool. The `stop_chunk` resolver refactor slightly widens the diff but removes a duplicated query and a 500-instead-of-404 inconsistency (covered by re-running the existing stop-path tests). No writes, no migration.

**A3 — Serve health (low).** Main risk is the internal-ish dashboard REST contract `GET /api/serve/applications/` (the same route `serve status`/the Serve CLI use, live in Ray 2.55.1) — a future Ray rename would break parsing. Mitigated by reading plain dict keys with `.get()` defaults (no `KeyError`; any non-healthy string → `not_ok`) and isolating the path in `_SERVE_APPLICATIONS_PATH`, exactly the pattern used for the `_RAY_KEY_*` cluster keys — the same risk class already accepted for `cluster_status`. Remote/KubeRay reachability of the path through `dashboard_url` (auth/proxy could differ) is open-question #2, but failure is graceful (`ok=False`/`not_ok`). The 3.0 s probe timeout could mark a slow-but-recovering controller `not_ok`; if that ever bites, the `_SERVE_HEALTH_TIMEOUT` module-level constant in `ray_dashboard.py` is a one-line edit — deliberately NOT a `RASK_*` env knob, since no operator is expected to tune a single-GET timeout.

**A4 — Smart cooldown (low-to-moderate).** **In-memory failure-history feasibility is the central question.** (1) No jitter is computed at all (deliberately not built — one in-process loop, no thundering herd), so there is no `PYTHONHASHSEED`/cross-process-reproducibility concern; `expires_in_secs` is the plain deterministic `min(base*2**(n-1), cap) - elapsed`. (2) `max(derived, pinned)` can keep a chunk quarantined slightly longer than Ray history alone after a genuine recovery — mitigated by decay-on-SUCCEEDED/RUNNING, which drops the entry the moment a green/active job appears. (3) Changing `Cooldown` from per-job to per-chunk and adding `OrchestratorState` fields is a response-shape change; backend-only, but call it out in the PR so the (out-of-scope) frontend can adapt — existing consumers see fewer `cooldowns[]` rows + new additive fields. (4) `derive_state` grows by four params; all call sites updated in the same pass. **No** data-loss/migration risk (in-memory), **no** new blocking IO or Ray round-trips.

**OTel (low-to-moderate).** (1) Global-instrumentation state leaking across tests — viewer tests share one process under `importlib`; any enabled-path test **must** uninstrument + reset providers in teardown, and the default-off path keeps existing tests untouched. (2) Forgetting `tp/mp.shutdown()` in the lifespan `finally` drops the last telemetry batch on clean exit — mitigated by placing it beside the existing disposes. (3) The job-failure counter is incremented per FAILED job inside `_per_chunk_fail_states` (the inner job grouping that survives A4's per-chunk rewrite), so it counts jobs not chunks; it may mildly over-count across ticks while a failure stays in a chunk's consecutive-failure tail — documented tradeoff; exact-once would need a seen-set we deliberately omit. (4) **Dependency weight / type stubs:** the instrumentation packages may ship partial stubs vs the project's `error-on-warning` `ty` config — verify `uvx ty check` is clean without suppressions before merge; and a train mismatch between `opentelemetry-sdk` and the `-instrumentation-*` packages can fail import, so pin them to one compatible release train. The feature is dead code unless `RASK_OTEL_ENABLED` is set, so production blast radius is minimal.

**Open questions carried from the surveys (for the owner):**
1. **A3 — htrflow as required vs informational.** v1 gates both `transcribe` and `htrflow` as required (a missing app → overall `not_ok`). If `htrflow` should be informational, it's a one-line per-name flag on the `_REQUIRED_SERVE_APPS` constant — deliberately not built now.
2. **A3 — remote/KubeRay reachability** of `/api/serve/applications/` through the same `dashboard_url` (auth/proxy may differ). Failure mode is graceful (`ok=False`), but worth confirming against the remote cluster.
3. **A3 — probe timeout** of 3.0 s: is that the right fast-fail threshold for a recovering controller, or should it be higher? It is a module-level constant (`_SERVE_HEALTH_TIMEOUT`), changed by editing one line — intentionally not an env knob.
4. **A4 — un-quarantine affordance.** Pre-NATS, a quarantined chunk is un-quarantined by (a) a manual `POST /chunks/{id}/submit` that yields a later SUCCEEDED/STOPPED job, or (b) viewer restart. Recommended: keep (a) as the only path this phase; add an explicit `POST /chunks/{id}/unquarantine` only if the owner wants un-quarantine-without-submit.
5. **A4 — default knobs:** `base=600 / cap=14400 / N=5` — confirm the 4 h cap and the N=5 quarantine threshold match operational expectations.
6. **OTel — response-size / log cap for A2** (cross-item): `?tail` is optional with no default cap (full log). Flag for the owner if a built-in default cap (e.g. last 1000 lines) is wanted.
