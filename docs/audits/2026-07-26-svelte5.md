## Part F — FINDINGS (ranked). Runes misuse + effects/lifecycle

### F1 — BUG (real, reachable): `@repo/ui` Select/Switch/RadioGroup expose no change callback, so four zones are forced into the documented `$effect`-writes-its-own-dependency anti-pattern — and one of them is a live display-vs-truth defect

**Root cause, in `@repo/ui`:**
`packages/ui/src/lib/components/slider/slider.svelte:20-21` *does* forward a change callback,
with the reason spelled out in the code:

```
/** Fires on user interaction only (not programmatic value changes) — lets a
 *  controlled scrubber seek without a bind:value ↔ update loop. */
onValueChange?: (value: number) => void;
```

The three sibling primitives do **not**:
- `packages/ui/src/lib/components/select/select.svelte:20-32` — props are only
  `value`(`$bindable`)/`options`/`placeholder`/`ariaLabel`/`disabled`. No `onValueChange`,
  even though the underlying `bits-ui` `Select.Root` supports one.
- `packages/ui/src/lib/components/switch/switch.svelte:5-9` — only `checked`(`$bindable`)/`class`.
- `packages/ui/src/lib/components/radio-group/radio-group.svelte:9-13` — only `value`(`$bindable`)/`options`/`class`.

Because "the user picked something" is not observable, every consumer reconstructs it with an
effect that **reads and writes the same state** — the exact shape the Svelte docs call an
escape hatch to avoid. All five sites, with the bound control they are compensating for:

| effect | bound control | writes a dep it reads? | converges? |
| --- | --- | --- | --- |
| `components/frontends/annotator/src/lib/select/DataSelection.svelte:103-107` | `<Select bind:value={datasetChoice}>` (`:162`) | yes (`datasetChoice`, `view`) | yes, via the `datasetChoice !== view?.id` guard |
| `components/frontends/annotator/src/lib/viewer/layout/LayerPanel.svelte:20-22` | `<Select bind:value={groupChoice}>` (`:42`) | yes | yes, via the `groupChoice !== controller.groupByColumn` guard |
| `components/frontends/media/src/lib/components/filter-popover.svelte:126-129` | `<Select bind:value={op}>` (`:206`) | yes (`op`) | yes |
| `components/frontends/media/src/lib/components/search-bar.svelte:119-123` | `<Select bind:value={kind}>` (`:287`) | yes (`kind`) | yes |
| `components/frontends/media/src/lib/components/search-settings.svelte:71-73` | `<Switch bind:checked={auto}>` (`:126`) + `<Slider bind:value={weightVal}>` (`:129`) | no | n/a — **it is broken in the other direction** |

**The one that actually misbehaves — `search-settings.svelte:69-73`:**

```
let auto = $state(weightPct === null);
let weightVal = $state(weightPct ?? 50);
$effect(() => {
    weightPct = auto ? null : weightVal;   // child → parent only
});
```

`weightPct` is a `$bindable` prop (`search-settings.svelte:26`). The effect pushes child→parent
and there is **no parent→child path**: `auto`/`weightVal` are copied from the prop once at mount
and never re-derived. The parent *does* replace `weightPct` externally:
- `components/frontends/media/src/lib/components/search-bar.svelte:65`
  `weightPct = s.weight === undefined || s.weight === null ? null : Math.round(s.weight * 100);`
  inside `adoptSpec()`,
- driven by `search-bar.svelte:78-83`'s `adoptSignal` effect,
- bumped by `components/frontends/media/src/routes/+page.svelte:203-206`
  `applySavedView() { void runSearch(next); searchBarAdopt += 1; }`,
- and `weight` **is** persisted in saved views —
  `components/frontends/media/src/lib/saved-views.ts:21-25` `stripEphemeral` deletes only
  `clean.image`.

Failure scenario (concrete): set the hybrid balance to 70 % vector and search; save nothing.
Apply a saved view that was captured in Auto/RRF mode. `adoptSpec` sets `weightPct = null`, the
search runs as RRF — but `auto`/`weightVal` in the child are untouched, so the Settings popover
still renders the slider at 70 % vector with the "70% vector" label
(`search-settings.svelte:76-82`). The panel now states a fusion balance that is not the one in
effect. The mirror-image case (apply a saved view carrying `weight: 0.3` while the child sits in
Auto) shows "Auto (RRF)" over a spec running at 30 %. In both cases the *next* touch of the
switch or slider silently overwrites the adopted value.

`SearchSettings` is mounted for the whole life of the bar (`search-bar.svelte:343`, not inside
the portalled popover content), so the stale locals persist — this is not fixed by reopening
the popover.

Note the parent's own comment at `search-bar.svelte:48-50` states the intent this breaks:
*"so the bar always shows what will actually run."*

**Verdict: BUG.** Fix: add `onValueChange`/`onCheckedChange` to `@repo/ui`'s Select, Switch and
RadioGroup (matching Slider, which already has it), then delete all five effects. Backward
compatibility is explicitly not a constraint in this repo, so the wrapper props can simply grow.

### F2 — BUG (real, cosmetic-severity): a `$effect` performs `goto()` on mount, firing one spurious client navigation + View Transition every time `/lineage/columns` is entered

`components/frontends/lakehouse/src/routes/lineage/columns/+page.svelte:28-32`

```
let selected = $state(page.url.searchParams.get('dataset') ?? '');
$effect(() => {
    const q = selected ? `?dataset=${encodeURIComponent(selected)}` : '';
    goto(`${base}/lineage/columns${q}`, { replaceState: true, keepFocus: true, noScroll: true });
});
```

The effect is unconditional, so it also runs on **mount**, when `selected` was just read *from*
the URL — i.e. it navigates to the URL the browser is already on. I verified SvelteKit 2.70.1
has no same-URL short-circuit: `goto` → `_goto`
(`components/frontends/lakehouse/node_modules/@sveltejs/kit/src/runtime/client/client.js:2328,2345`)
→ `navigate()` (`:1712`), which runs `_before_navigate`, `load_route`, and fires every
`onNavigate` callback (`:1911` `Array.from(on_navigate_callbacks, fn => fn(nav.navigation))`)
with no equality test against the current URL anywhere in the path.

The lakehouse layout registers exactly such a callback —
`components/frontends/lakehouse/src/routes/+layout.svelte:48-56` calls
`document.startViewTransition(...)` — so entering the Columns page runs a full client
navigation and a view transition it did not need. Deep-linking in with `?dataset=X` makes it
worse: it is a real replaceState round trip before the user has done anything.

This is the docs' "do not use an effect to connect one value to another" case: the write should
hang off the picker's change, not off `selected`.
**Verdict: BUG** (no user-visible data loss; a wasted navigation + an unwanted animation).
Fix: move the `goto` into the picker's change handler (which F1's `onValueChange` enables), or
at minimum guard with `if (selected !== (page.url.searchParams.get('dataset') ?? '')) goto(...)`.

### F3 — BUG (small, real): a debounced search effect has no cleanup, so its timer + fetch outlive the component

`components/frontends/media/src/routes/graph/+page.svelte:346-359`

```
let searchTimer: ReturnType<typeof setTimeout> | undefined;   // :345 — plain let, correct
$effect(() => {
    const q = searchQ.trim();
    clearTimeout(searchTimer);
    if (q.length < 2) { matches = []; return; }
    searchTimer = setTimeout(() => {
        void searchGraphEntities(q).then((r) => { matches = r.matches; dropdownOpen = r.matches.length > 0; });
    }, 250);
});                                                            // ← no cleanup return
```

The top-of-body `clearTimeout` covers *re-runs*, but not teardown: navigate away within 250 ms
of typing and the timer still fires, issuing a `searchGraphEntities` request for a page that no
longer exists. Every sibling debounce in the repo returns the cleanup —
`packages/ui/src/lib/components/search-bar/search-bar.svelte:60` `return () => clearTimeout(timer);`,
`components/frontends/media/src/lib/atlas/AtlasTooltip.svelte:117`,
`components/frontends/media/src/lib/workflow/FlowPane.svelte:51` — so this is drift, not a
deliberate choice (no comment claims otherwise).
Confirmed *not* a loop: `searchTimer` is a plain `let`, not `$state`, so the in-body
assignment creates no dependency.
**Verdict: BUG** (leak, low blast radius). Fix: `const timer = setTimeout(...); return () => clearTimeout(timer);`

### F4 — DEVIATES (no reason in code): `bind:value` onto a `$derived`, relying on writable-derived override semantics

`components/frontends/annotator/src/lib/viewer/layout/LayerPanel.svelte:19-22,42`

```
let groupChoice = $derived(controller.groupByColumn);
$effect(() => {
    if (groupChoice && groupChoice !== controller.groupByColumn) controller.setGroupBy(groupChoice);
});
...
<Select bind:value={groupChoice} … />
```

`bind:` writes into a `$derived` — legal only because Svelte ≥ 5.25 lets a `let`-declared
`$derived` be reassigned, and the override is discarded the instant any dependency changes.
It converges (pick → override → effect → `setGroupBy` → derived recomputes to the same value →
guard fails), and the compiler is silent (Part B), but any other writer of
`controller.groupByColumn` landing between the pick and the effect flush silently drops the
user's selection. This is the single most fragile reactive shape in the four zones and the only
one with **no explanatory comment**.
**Verdict: DEVIATES** (works today; would be deleted outright by F1's `onValueChange`).
