## 1. Answer in one paragraph

Verification: all 11 headline claims in this document were adversarially verified against code and live probes and CONFIRMED (§7).

Yes, the read-through is complete: every section of `lance_docs/` was read by a dedicated reader and distilled into the rules in §5. Against those rules rask is on the right side of the important create-time decisions (2.2 storage version, stable row ids, blob v2, conditional-PUT commits, per-worker fragments with one commit, run-id replay marker) and on the wrong side of the operational ones (no shared `lance.Session`, no thread pinning under Ray, conflict classification only on one door, dead FRI path, no primary key declaration). On the REST surface the route grammar is spec-verbatim for all 54 ops, but only 12 ops are usable exactly as the spec describes them, and a stock Lance client cannot use 5 of them at all today. The gap is not architectural. It is a fixed list of wire-shape fixes (§3) plus moving rask's governance routes off the spec surface onto a management API (§4). That is the work that makes "spec-verbatim is a hard goal" true.

### Identity, context and error model

IDENTITY (namespace.md:1129-1141: api_key→x-api-key, auth_token→Authorization: Bearer, headers beat body): PARTIAL. `Authorization: Bearer` is read by HTTPBearer(auto_error=False) (services/catalog/src/catalog/api/security.py:36-38) but verified ONLY when LANCE_OIDC_ENABLED (default False, core/config.py:181; security.py:168-181 → 401 code 16 'Missing bearer token' when on, ignored when off). `x-api-key` is read NOWHERE (ripgrep -i 'x-api-key|api_key' over services/catalog/src → no hits; service-kit → no hits): a client authenticating by api_key is anonymous. The shipped RestNamespace client DOES send both headers from `header.x-api-key` / `header.Authorization` properties (probed). rask additionally consumes non-spec headers dapr-api-token, x-lance-service-identity, dapr-caller-app-id (security.py:45-49), x-lance-originator (api/dependencies.py:260-271) and X-Lance-Run-Facets (endpoints/data.py:114,467). Body `identity` fields are accepted by the pydantic models and never read. CONTEXT (namespace.md:1143-1183: request context header.<name> ↔ HTTP headers, every response header echoed as header.<name>): NOT IMPLEMENTED in either direction (ripgrep 'header\.' over services/catalog/src and service-kit → only an unrelated docstring in service_kit/governed/dapr_auth.py:59); response `context` is never populated and response_model_exclude_none drops it. Mitigating fact (probed): the pylance 10.0.0 Rust client itself sends request `context` inside the JSON body (`{"context":{"header.x-trace-id":"tr1"},...}`) rather than as headers, so today neither side implements the mapping; the SKILL.md:32-36 text describes the spec rule, not rask behaviour. ERROR MODEL: problem+json (media application/problem+json, service_kit/lakehouse/ns_errors.py:22) carrying RFC 9457 fields PLUS the spec's required `code` and `error` (ns_errors.py:99-108) — the reference client parses this fine (probed: 404 body with code 4 → TableNotFoundError(4); 501 with code 0 → UnsupportedOperationError). All 24 ErrorCodes are mapped (ns_errors.py:24-54) with one status deviation: UNSUPPORTED → 501 (ns_errors.py:25) where spec.yaml:6576-6589 shows 406 (client dispatches on code, tolerated). The BREAKING gaps are the bodies with NO `code`: FastAPI RequestValidationError → 422 {type,title,status,errors} (ns_errors.py:135-146; probed on POST query with missing k: 422), generic Exception → 500 {type,title,status,detail} (ns_errors.py:148-161), FastAPI's own 405/404 `{"detail":"Method Not Allowed"}` (probed GET count_rows → 405), and maintenance 503 (api/maintenance_mode.py:31-43); the reference client turns EVERY one of these into InternalError 18 'Failed to parse error response … missing field `code`' (probed). ## 3. The blockers to spec-verbatim, with fixes

Ordered by impact. Each is a bounded change in `services/catalog`; none needs a redesign.

### B1. Bodyless handlers ignore the spec's REQUIRED JSON request body, so a spec client's version/tag/branch/vend_credentials/pagination are silently dropped and path/body id mismatch is never 400: DescribeTable (tables.py:270-283 — rask takes version/tag/vend_credentials as QUERY params instead), ListTableIndices (indices.py:97-107, query-only page_token/limit; body version/branch/page_token/limit ignored), GetTableStats (tables.py:903-907, branch dropped), DescribeTableIndexStats (indices.py:110-114), DescribeNamespace/NamespaceExists/TableExists/DeregisterTable/DescribeTransaction (id reconciliation skipped). The shipped RestNamespace client sends vend_credentials ONLY in the body (probed), so credential vending is unreachable by any spec client and a private-bucket table cannot be opened without a rask SDK.

**Fix.** Declare the lance_namespace request model as the body on every op (`body: DescribeTableRequest`), run reconcile_body_id (identifiers.py:66-73) uniformly, read version/tag/branch/vend_credentials/page_token/limit from the body (keep rask's query aliases only as fallbacks that lose to the body), and add a wire-level conformance test that posts each spec body and asserts it is honoured (test_spec_conformance.py only compares (method, path)).

### B2. Three response shapes the reference client cannot deserialise: UpdateTableSchemaMetadata answers the wrapped `{metadata:{...},transaction_id}` where the spec's REST-only rule is the direct {str:str} map (client error 'invalid type: map, expected a string'); ExplainTableQueryPlan/AnalyzeTableQueryPlan answer text/plain unquoted strings where spec.yaml declares application/json string (client error 'expected value'); CountTableRows answers text/plain (a bare number parses, so it survives only by accident).

### B3. HTTP-method mismatch with the shipped client: pylance 10.0.0 RestNamespace sends GET /v1/table/{id}/count_rows and GET /v1/table/{id}/tags/list; rask mounts both as POST only, so the client gets FastAPI's 405 `{"detail":"Method Not Allowed"}` and, lacking `code`, raises InternalError 18. The vendored spec.yaml says POST for both, so this is spec-revision drift between the client rask's own venv ships and the spec rask vendors — but 'any Lance client connects with no rask SDK' is judged by the client.

**Correction after reading the sources (2026-09-02).** This is not spec-revision drift. The spec says POST at every tag from v0.9.0 to v0.12.0, and lance-namespace's own generated Rust client (`lance-namespace-reqwest-client`) sends POST at every tag. The GET comes from the REST client that **pylance bundles from the lance repository itself** (`rust/lance-namespace-impls/src/rest.rs`: `count_table_rows` and `list_table_tags` call `get_json`, at tag v10.0.0 and at main today), and the reference **server** pylance bundles (`rest_adapter.rs`) mounts the same two routes as GET. So the lance repo disagrees with its own spec on both sides of the wire. rask's dual-mount is still the right local fix; the upstream fix is a one-line change in lance, worth filing.

**Fix.** Serve both forms for count_rows and tags/list (GET with query params, POST with body) until the client and the vendored spec agree, and record which spec revision each supported client implements; give every framework-generated 404/405 a coded problem body (see blocker 5).

Evidence:

### B5. Error bodies without the spec-required `code`: 422 for pydantic validation (spec says 400/code 13), generic 500, FastAPI's default 404/405, and the maintenance 503 — the reference client cannot parse any of them and surfaces InternalError 18 instead of the real condition. Plus: UNSUPPORTED → 501 where the spec shows 406; protection refusals reuse code 3 on table ops; tag/branch failures on the dataplane are unmapped ValueError/OSError → 500 (codes 8/9/11/22/23 unreachable); column/data ops never mint 14/20.

**Fix.** Map RequestValidationError → InvalidInputError (400, code 13); make the catch-all handler emit code 18; install coded 404/405 handlers (HTTPException → problem body with code); give the maintenance 503 code 17; translate pylance 'Ref conflict'/'Ref not found'/'Version not found'/branch OSErrors to codes 9/8/11/22/23 in dataplane.create_tag/update_tag/delete_tag/create_branch/delete_branch; catch commit conflicts → 14 and schema failures → 20; decide 406 vs 501 with the owner (client dispatches on code, so either is parseable).

## 5. How the docs say to build it: the rules digest

Every rule cites the doc lines it comes from and, where relevant, where rask does or does not follow it. These are the practices a Lance-native, BYO-engine lakehouse has to honour; §6 lists where rask deviates.


### Build rules (every write path)

- BR1 CREATE-TIME FLAGS ON EVERY CREATE PATH. Every dataset is created with data_storage_version="2.2" and enable_stable_row_ids=True, including write_fragments against a not-yet-existing dataset; both are fixed at creation and a later set is a silent no-op (file_format.md:4007-4015; guide.md:228-230, 258-272). rask: dataplane.py:249-263, ingest lander.py:70,270-284 CREATION_FLAGS, medallion compute.py:229-235; ingest verifies the flag on existing datasets (ingest/catalog.py:108-149).
- BR2 THE COMMIT IS ONE ATOMIC PUT-IF-NOT-EXISTS OF A MANIFEST. Rely on the store's conditional PUT (verified per store) or on an external manifest store with put-if-not-exists; never on plain PUT (file_format.md:4763-4772, 5375-5381). rask verifies RustFS If-None-Match (records.py:7-10; tests/e2e-py/test_object_store_cas_e2e.py).
- BR3 DISTRIBUTED WRITE = write_fragments PER WORKER, ONE commit(read_version) ON ONE NODE. Serialize FragmentMetadata.to_json (json.dumps it), key fragments by unit not id (every worker's first fragment is id 0), commit Append/Overwrite once (guide.md:1533-1601, 1574-1578, 1621-1637). rask: dataplane.py:640-690; lander.py:255-284.
- BR4 CLASSIFY EVERY COMMIT CONFLICT AS REBASABLE / RETRYABLE / INCOMPATIBLE and never collapse them into one 409; an INCOMPATIBLE conflict (Append vs Overwrite/Restore) must never be advised to retry (file_format.md:5251-5267, 5318-5373). rask does this for /commit only (dataplane.py:556-596).
- BR5 APPEND NEVER CONFLICTS WITH APPEND, so the format cannot deduplicate a replayed commit; idempotency is an application marker (commit_message / transaction property) that a retry recognises (file_format.md:4811-4833). rask: rask.ingest.run_id marker, dataplane.py:598-637,675-690.
- BR6 PREFER NARROW TRANSACTIONS. Append, DataReplacement, Rewrite over Merge (Merge is 'overly general', retryable against every data op); Overwrite and Restore trump/void everything and must be owner-gated and serialised (file_format.md:5008-5030, 5077-5082, 4887-4895).
- BR7 SCHEMA CHANGES RUN WHEN NOTHING ELSE WRITES; alter_columns with a type change drops the column's index; nullable→non-nullable is impossible (guide.md:606-610, 830-833; lance_sdk.md:4277).
- BR8 STORAGE OPTIONS ARE PER-DATASET, NOT PROCESS ENV. Pass storage_options on every open/write; S3-compatible stores need BOTH region and endpoint; allow_http only for an http:// endpoint; explicit options beat env vars (guide.md:2306-2330, 2338, 2410-2438).
- BR9 ONE BOUNDED lance.Session PER PROCESS. Every bare lance.dataset() mints a 1 GiB metadata + 6 GiB index cache pair and discards it; share one Session (keys are (uri, version, etag), so it is safe for mutating services) and size it to the pod (guide.md:2996-3029; lance_sdk.md:3660-3665).
- BR10 ROWS ARE NOT A UNIT OF MEMORY. Peak scan memory ≈ 2×io_buffer_size + batch_size×compute_threads; set batch_size by bytes (blob rows), and raise io_buffer_size with LANCE_IO_THREADS (guide.md:3031-3053, 2965-2981).
- BR11 UNDER RAY, PIN LANCE_CPU_THREADS (and LANCE_IO_THREADS) in runtime_env.env_vars: the compute pool defaults to ALL host cores per process and Lance workers oversubscribe a node (guide.md:2982-2988).
- BR12 FRAGMENT SIZE FOLLOWS ROW WIDTH, NOT A GLOBAL ROW COUNT: default 1M rows/fragment to ~1B rows; 10-100 GB reasonable upper range, 1 TB hard ceiling; more fragments when many concurrent update/delete/merge_insert (guide.md:3076-3111).
- BR13 TAGS ARE THE ONLY GC-PROOF PIN. Tag a version before a slow gate or a destructive drop; cleanup must skip tagged versions (error_if_tagged_old_versions=False), and a tag must be deleted before its version can be reclaimed (guide.md:3851-3858, 745-777; lance_sdk.md:3818-3825).
- BR14 REFUSE UNKNOWN FEATURE FLAGS BEFORE ANY REWRITE. Known bits: 1 DELETION_FILES, 2 STABLE_ROW_IDS, 4 deprecated, 8 TABLE_CONFIG (writer), 16 BASE_PATHS; bits ≥32 mean 'unsupported' — measured in rask, compacting a shallow clone materialised shared data (file_format.md:5441-5474; features.py:57-95).
- BR15 OBSERVABILITY IS OPT-IN: pylance[otel] + lance.otel.instrument_lance_metrics() ONCE per process; LANCE_LOG (replaces RUST_LOG) filters Rust logs; lance::io_events fire only on cache miss; lance::object_store::throttle shows AIMD rate drops (guide.md:2805-2878, 2883-2963, 3055-3074).
- BR16 DISTRIBUTED INDEXING = uncommitted segments per fragment subset, then ONE commit of segments with DISJOINT fragment coverage (create_index_uncommitted / commit_existing_index_segments / merge_existing_index_segments); IVF-PQ segments meant to merge physically share centroids + codebook; uncommitted dirs are aged out by cleanup (guide.md:1336-1467, 1512-1515).
- BR17 VECTORS: FixedSizeList<float> only, dims divisible by 8, ANN index past ~10k rows, query distance_type MUST equal the trained metric (silently wrong otherwise), ANN/KNN require a limit (guide.md:1064-1067, 1287-1308; lance_sdk.md:5488, 1466-1475).
- BR18 create_index / create_scalar_index DEFAULT replace=True — an 'ensure index' MUST list first or it rebuilds every call; drop_index leaves files until optimize/cleanup runs (lance_sdk.md:3973-3976, 3992). rask: dataplane.py:1429-1450.
- BR19 DECLARE AN UNENFORCED PRIMARY KEY via lance-schema:unenforced-primary-key field metadata when merge_insert dedup is the write path; it is fixed after first set and uniqueness is NOT validated (file_format.md:2887-2910; lance_sdk.md:3853-3860).
- BR20 BRANCHES ARE SHALLOW CLONES REFERENCING THE SOURCE ROOT BY ABSOLUTE PATH: validate branch/tag names at the door (no 'main', no '.lock', no '/' in tags), lance.dataset(root) opens only main, and moving/renaming a root strands every branch (file_format.md:2707-2778, 2784-2820). rask refuses rename with branches (dataplane.py:401-428).

### Multimodal rules (blobs, media, JSON)

- MM1 Blob columns are blob_field / blob_array (lance.blob.v2) on a ≥2.2 dataset; the legacy lance-encoding:blob metadata is REJECTED on write at ≥2.2 and the two schemes are mutually exclusive; migration is a chunked rewrite into a new dataset (guide.md:264-272, 528-564, 580-586).
- MM2 Inline binary vs blob: inline only for payloads under a few tens of KB that are read whole; blob when partial/streaming reads are needed OR average ≥ ~1 MB, because compaction re-copies inline payloads into every new version but references .blob files (guide.md:566-574). rask bronze payload is blob (ingest/runtime.py:42-52); thumbnails inline (derivers.py:74-75).
- MM3 Pin blob placement thresholds PER COLUMN (inline_size_threshold, dedicated_size_threshold): they persist in the schema and an append naming different values is rejected; dedicated is checked first; doc default 16 KiB / 2 MiB vs rask-measured 64 KiB / 4 MiB on pylance 10.0.0 — unconfirmed which is right, so pin (guide.md:322-331; ingest/runtime.py:26-33,55-71).
- MM4 External-URI blobs must fall under a base registered at CREATE (initial_bases, is_dataset_root=False); allow_external_blob_outside_bases stays False estate-wide; registered bases are not readable back from pylance so a producer must stamp its base into schema metadata to carry descriptors forward (guide.md:319-321; dataplane.py:222-233; service_kit/lakehouse/blobs.py:53-116).
- MM5 Choose the blob read API by shape: read_blobs for whole payloads, take_blobs only for seek/range, scanner(blob_handling="all_binary") for row-aligned bulk reads; never thread-pool take_blobs; exactly one of ids/indices/addresses, and only ids (stable row ids) survive compaction (guide.md:391-408, 442-462, 589-591).
- MM6 Null and zero-length blobs are one stored state; guard take_blobs results ([] on pylance ≤9, None slot on 10.0.0) and prove reachability with a real read_range, not size() (guide.md:290-304; dataplane.py:827-838; blobs.py:157-192).
- MM7 Semi-structured data is pa.json_() (stored JSONB as lance.json); writers emit '{}'/'[]' never ''; json_get_*/json_extract/json_exists are FILTER-only (no projection), strictly typed; a JSON scalar index is built on ONE path literal and only serves a filter using the same literal; overwrite drops it so rebuild after each overwrite (guide.md:1798-1821, 2040-2062, 2181-2184; medallion compute.py:250-262).
- MM8 Prefer typed Struct/List/Map (Map needs 2.2) for fixed-shape nested data; JSON only for genuinely schemaless payloads; keep nesting flat (guide.md:1169-1231, 2168-2175).
- MM9 Maintenance on blob tiers sizes the scan batch by bytes (rask: 64 rows for ~1.8 MB rows, chart/values.yaml:1171-1183) and treats data/<stem>/*.blob sidecars as referenced by their data file in any orphan scan (guide.md:571; orphans.py:192-200).
- MM10 The platform's shared seams stay modality-agnostic: governed rows are {id, payload(opaque), stage, lineage, source_rowid}; any modality-specific shape, model or decoder lives in a sealed runner (CLAUDE.md Architecture; medallion/schemas/tier.py). Extension arrays (ImageURIArray, EncodedImageArray, BFloat16) are client-side conveniences, not storage rules (guide.md:31-203).

### Catalog rules (the REST surface)

- CR1 BASIC vs FULL. The spec's recommended minimum is 8 metadata ops: CreateNamespace, ListNamespaces, DescribeNamespace, DropNamespace, DeclareTable, ListTables, DescribeTable, DeregisterTable — with DropNamespace only needing Restrict and DescribeTable only needing the defaults (return location without opening the dataset). Everything else (54 ops total) is optional and the Lance SDK fulfils it client-side against the location (ns_catalog/namespace/operations/index.md 'Recommended Basic Operations'). rask routes 54/54, 47 backend-backed, 7 spec-correct 501 (SKILL.md:18-24).
- CR2 WHY NOT CreateTable/DropTable in the minimum: they are DATA operations (long-running, non-atomic on failure, CTAS needs staging/multi-statement transactions); the catalog should own DeclareTable/DeregisterTable and let CreateTable/DropTable be composed from those + the SDK (operations/index.md 'Why Not CreateTable and DropTable?'). A REST catalog MAY still serve them (rask does: data.py:98, tables.py:348) but must then own the atomicity/cleanup (rask: trash + undrop, tables.py:348-405, 605).
- CR3 EXTERNAL MANIFEST STORE = the version-management ops (CreateTableVersion, BatchCreateTableVersions, DescribeTableVersion, ListTableVersions, BatchDeleteTableVersions, BatchCommitTables). When used, commits are coordinated THROUGH the catalog before the manifest is written to storage — governance (audit, access control, commit validation) rides there — while the Lance table on storage stays the authoritative state (catalog/rest/index.md 'External Manifest Store'; dir/index.md 'Table Version Management' with table_version_management=true in __manifest metadata; four-step protocol file_format.md:5375-5439).
- CR4 DUALITY. REST request/response bodies ARE the Namespace Client models; `id` is optional in the body because it is in the route; if both are present and differ the server MUST 400; if the body omits it the route wins (operations/index.md 'Duality'; rest/index.md 'Standard Operations'). rask: identifiers.py reconcile_body_id.
- CR5 NON-STANDARD OPS (the only divergences): List* are GET with page_token/limit query params; DescribeTable carries ONLY with_table_uri, load_detailed_metadata, check_declared as query params — version, tag, branch, vend_credentials stay in the REQUIRED JSON body; CreateTable/InsertIntoTable/MergeInsertIntoTable take Arrow IPC bodies with fields as query params/headers; QueryTable returns Arrow IPC file; CountTableRows/ExplainPlan/AnalyzePlan return plain values; UpdateTableSchemaMetadata bodies are bare maps (rest/index.md 'Non-Standard Operations'; spec.yaml:395-417, 2786-2830).
- CR6 ROUTE GRAMMAR: POST /v1/<object>/{id}/<action> — everything a reverse proxy needs for routing/authN/authZ is in the PATH, never only in the body; identity maps api_key→x-api-key, auth_token→Authorization: Bearer; context maps to headers; headers beat body (rest/index.md 'REST Routes', 'Identity Header Mapping').
- CR7 ADAPTER vs IMPLEMENTATION: any HTTP server implementing the OpenAPI is a Lance REST Catalog server; one that proxies an existing metadata service is an ADAPTER; an implementation is a per-language library. Prefer an adapter for multi-language reach and tool support; prefer an implementation for security (no man-in-the-middle) and performance (one less hop) (rest/index.md 'REST Catalog Server and Adapter', 'Choosing between'). rask is a REST server fronting the native dir implementation (native.py:1-40; config.py LANCE_REST_IMPL=dir).
- CR8 THE CLIENT DOES THE DATA WORK unless pushed down: lancedb/pylance resolve describe_table → location + storage_options and run reads/writes themselves; namespace_client_pushdown_operations selects what the server executes. A server must therefore vend a usable location and (on vend_credentials) storage_options with expires_at_millis, and honour version/branch from the body (lance_sdk.md:37-39, 343-357; ray.md:298,397; spec.yaml:2872-2878).
- CR9 ERRORS: 24 numeric codes, identical across Python/Java/Rust/REST, carried as RFC 9457 problem+json; clients dispatch on the code (operations/errors.md; SKILL.md:39-49; ns_errors.py maps Throttling→429, Unsupported→501, Concurrent→409).
- CR10 DIRECTORY CATALOG V2: __manifest is a Lance table whose object_id is the unenforced PK; implementations MUST enforce uniqueness via merge-insert with PK dedup and MUST atomically detect a concurrent write of the same entry; tables live at <hash>_<object_id> with '$' separators; root properties live in the manifest's schema metadata (dir/index.md 'Manifest Table Schema', 'Manifest Table Commits').
- CR11 ANYTHING NOT ONE OF THE 54 OPS IS NOT THE PUBLIC API. Under the owner's verbatim goal, rask's extra routes on /v1/table — /{id}/commit, /{id}/blobs, /{id}/credentials, /{id}/maintenance/{preview,run,compact}, /{id}/protection, /{id}/tasks, /{id}/undrop, /{id}/history — belong on the separate management API (spec.yaml path list lines 84-2254 has none of them; data.py:326,632; credentials.py:44; maintenance.py:24-49; tables.py:569-605; versions.py:47).

### Maintenance rules

- MR1 FIXED ORDER, ONE OWNER: compact_files → optimize_indices → cleanup_old_versions per dataset; a policy may skip a step, never reorder; never two reclaimers on one dataset (auto_cleanup on the commit path XOR the sweep) (guide.md:3642-3660, 3738-3798; optimize.py:153-161, 330-378; service.py:7).
- MR2 cleanup_old_versions: explicit retention (pylance 10.0.0 substitutes 14 days when neither bound is given, the guide says 7 — version-dependent); delete_unverified=True ONLY when no writer can be in flight longer than older_than (otherwise corruption); tagged versions and branch-referenced files are exempt; enable_auto_cleanup is itself an update_config commit that mints a version (guide.md:3665-3736; lance_sdk.md:4405-4411; optimize.py:319-385).
- MR3 COMPACTION vs INDEX BUILD: without stable row ids or a Fragment Reuse Index, Rewrite vs CreateIndex on overlapping fragments is a retryable conflict and compaction (the longer op) loses repeatedly, degrading layout; use defer_index_remap=True (FRI) OR stable row ids — pylance refuses the combination in both directions; a FRI needs a periodic trim once every index post-dates a reuse version (file_format.md:2184-2238, 4931-4944; guide.md:3127-3151; optimize.py:254-277).
- MR4 REWRITE requires ReserveFragments first; distributed compaction = plan on one node, execute on many, commit once (file_format.md:4946-4960, 5084-5100). rask compacts in-process (optimize.py:254-277); lance-ray 0.5.0 compact_files measured as not compacting (tests/e2e-py/test_ray_batch_e2e.py:86-99).
- MR5 REFUSE BEFORE REWRITE: check reader/writer feature flags (unknown bit ⇒ unsupported), refuse compaction on FLAG_BASE_PATHS datasets, refuse GC on a source another manifest resolves through, refuse anything with _mem_wal/ (file_format.md:5441-5474, 3744-3752; features.py:57-95; optimize.py:184-224; orphans.py:81-84,291-307).
- MR6 SIZE PER TIER: target_rows_per_fragment by row width (rask bronze 512 / silver 262,144 / gold 524,288), batch_size by bytes, num_threads by pod cpu not host cores (guide.md:3076-3111, 3037-3053; tiers.py:1-40; config.py:44-65).
- MR7 REPORT WHAT optimize_indices CANNOT FIX: unindexed rows/fragments, delta fan-out, missing expected indices; index_stats PANICS (pyo3, BaseException) on a JSON index — contain it, never let it discard a completed compaction (file_format.md:1108-1128; index_health.py:65-146; optimize.py:300-318).
- MR8 OVERWRITE DROPS INDICES and hard-conflicts with CreateIndex/Rewrite; rebuild after every overwrite (file_format.md:4926-4929; medallion compute.py:250-262).
- MR9 drop_index detaches only — files stay until optimize/cleanup; alter_columns type change drops the index (lance_sdk.md:3992; guide.md:830-833).
- MR10 SHALLOW CLONES AND BRANCHES SHARE FILES: cleanup on either side can delete what the other references — measured in rask; protect source roots and refuse the sweep on clones (lance_sdk.md:3677-3692; features.py:25,85; optimize.py:196-224).
- MR11 migrate_v2_manifest_paths needs exclusive access and must run to completion (lance_sdk.md:4437-4459). Not adopted by rask (no references; unconfirmed whether created tables already use V2 naming).
- MR12 ORPHAN SCAN: .txn files accumulate by design, latest_version_hint.json is structural and never authoritative, _deletions/ and _indices/{uuid} are referenced by any live version, .blob sidecars belong to their data file (file_format.md:3236-3244, 4783-4796; orphans.py:15-31, 90-93, 192-200).

### Compute rules (BYO workers, lance-ray)

- CP1 RESOLVE THROUGH THE NAMESPACE, NOT A PRE-BAKED URI: a BYO worker connects with lance_namespace.connect("rest", {uri, delimiter?, header.Authorization}) (impl + properties are what lance-ray ships to workers), calls describe_table(id, vend_credentials=true[, version|branch]) and uses location + the returned storage_options merged with its own (ray.md:44-50, 298, 397; .venv lance/namespace.py:919-926; spec.yaml:2786-2878).
- CP2 WRITE PROTOCOL: (1) read_version = describe/version at read time; (2) each worker lance.fragment.write_fragments(batch, location, data_storage_version="2.2", enable_stable_row_ids=True, storage_options) — the flags are mandatory when the dataset may not exist yet; (3) ship json.dumps(FragmentMetadata.to_json()) keyed by unit; (4) ONE node commits LanceOperation.Append(frags) (or Overwrite with read_version=0 / Merge for add-column / Update for update-columns) with read_version; (5) carry an idempotency marker in commit_message and check for it before re-committing; (6) on error obey the taxonomy: 400 schema/no-base → fix the data, 400 incompatible → discard fragments and re-WRITE, 409 → re-read + re-commit, 503 → back off (guide.md:1542-1637, 1674-1681, 1763-1769; file_format.md:5251-5267; dataplane.py:556-690; lander.py:117-160,255-284).
- CP3 INDEX PROTOCOL: workers create_index_uncommitted(column, fragment_ids=subset) → coordinator commit_existing_index_segments / merge_existing_index_segments with DISJOINT coverage; only INVERTED/FTS/BTREE/BITMAP scalar and IVF_FLAT/IVF_SQ/IVF_PQ vector types are distributed; distributed IVF training needs ≥ num_partitions × sample_rate(256) rows — gate to a local build below that; replace defaults True (guide.md:1336-1467; ray.md:185-314, 558-602; ratch indexing.py:26-28,80-125).
- CP4 COMPACTION PROTOCOL: ReserveFragments, then rewrite on workers, then one Rewrite commit; with defer_index_remap the Rewrite carries an FRI and two concurrent deferred compactions are a retryable conflict; num_workers is clamped to fragment count; then optimize_indices, then cleanup (file_format.md:4946-4992; ray.md:18-84, 593-595).
- CP5 RAY ENVIRONMENT: runtime_env.env_vars carries LANCE_CPU_THREADS (and LANCE_IO_THREADS / io_buffer_size) so several Lance processes per node do not each claim every core; dependencies ship as per-workload baked images via runtime_env.image_uri, never runtime_env.pip/uv (guide.md:2965-2988; CLAUDE.md runners ruling). rask's ray_submit.py:105-125,242-287 carries OTEL_* only (OPEN-WORK.md H2).
- CP6 lance-ray SPECIFICS a BYO worker inherits: write_lance defaults min_rows_per_file 1,048,576 / max 67,108,864; target_bases must match registered bases; it demotes blob-v2 columns to LargeBinary (rask-measured) so media stages take a pylance path; vector_search opens ONE fixed version and assigns work by index-segment ownership (ray.md:838-875, 357-412; scripts/ray_stage_job.py:13-19).
- CP7 WHAT THE CATALOG MUST EXPOSE FOR ALL OF THE ABOVE: describe_table honouring body version/branch/vend_credentials with location + expiring storage_options; list_tables per namespace (compact_database) and a root list that is not empty; declare/register for write-mode creates; the version-management ops if it wants to sit in the commit path (external manifest store); batch-commit for multi-table atomicity; 409 for retryable conflicts, 400 for incompatible ones, 429 + Retry-After for load-shed (spec.yaml:395-417, 668-921; rest/index.md; load_shed.py:82-104). rask today: describe binds those fields from the query string (tables.py:271-283), version ops delegate to the dir backend (versions.py:38-41), batch_commit/alter_transaction 501 (SKILL.md:21-23), root list_namespaces is seeded from the warehouse registry (tables.py:100-138).
- CP8 THE PLATFORM SUBMITS, IT DOES NOT COMPUTE: Lance ships no scheduler; the driver (lance-ray, ratch, a slurm/k8s job) owns worker fan-out and the single commit; the catalog never runs the UDF/backfill itself (guide.md:1326-1332, 1527-1529; ray.md:140-169). rask's computed/backfill_columns answer 501 for exactly this reason (dataplane.py:1063-1081).

### Hard constraints of the format (things that cannot be designed around)

- Stable row ids and data_storage_version are create-time-only; write_fragments defaults resolve to 2.1 + no stable ids and the later commit fails 'added files with version 2.1 ... data storage version is 2.2' (file_format.md:4009-4015; guide.md:228-230; lander.py:270-284).
- Indices reference row ADDRESSES today; stable-row-id support in indices is 'in progress' and marked experimental — rask's row-level lineage rests on it (file_format.md:3958-3966, 1274-1280).
- defer_index_remap=True is refused on datasets WITH stable row ids ('nothing to defer') and WITHOUT row_addrs; FRI and stable row ids are mutually exclusive in practice (optimize.py:255-277; tests/unit/test_maintenance_optimize.py:361-380).
- Restore trumps every operation; anything built against a concurrently restored/overwritten version is INCOMPATIBLE and retrying may silently produce different results (file_format.md:5077-5082, 5263-5267, 5346-5373).
- Merge is retryable against every concurrent data op and incompatible with Project; Clone must be the first operation in a dataset; Rewrite needs ReserveFragments (file_format.md:5008-5030, 5121-5124, 4950-4952).
- Feature-flag bits ≥32 must reject; 1/2/16 are reader+writer required, 8 writer-only, 4 deprecated (file_format.md:5452-5474).
- Branch names: not 'main', no '.lock' suffix, no '..'/'\\'/'//', segments alnum . - _; tag names cannot contain '/' or start/end with '.'; tags always live at the dataset root (file_format.md:2707-2720, 2784-2820).
- External manifest store: an unaware reader lags at most one commit; a reader finding a UUID-suffixed manifest must finish the copy or refuse; the store supplements, never replaces, object-store manifests (file_format.md:5379-5381, 5406-5439).
- latest_version_hint.json is never authoritative; .txn files accumulate for failed attempts (file_format.md:3236-3244, 4783-4796).
- Unenforced PK: non-nullable leaf, not under list/map, fixed after first set, uniqueness NOT validated (file_format.md:2891-2899).
- Blob v2 and Map columns need ≥2.2; legacy blob metadata is rejected at ≥2.2; thresholds persist in the schema and differing appends are rejected; external URIs must map to a registered base unless allow_external_blob_outside_bases=True (reference mode only) (guide.md:258-272, 322-329, 319-321, 1211; .venv lance/dataset.py:7571-7582).
- JSON functions are filter-only; json_get_* are strict (null on mismatch); json_array_length errors on non-array; a JSON index matches one path literal (guide.md:1829-2008, 2040-2062, 2181-2184).
- HTTP client defaults: connect 5s, request 30s, 3 retries, 180s retry timeout; AIMD throttle on 429/503 with initial 2000 / max 5000 req/s; S3-compatible stores require region AND endpoint; allow_http defaults False (guide.md:2336-2348, 2410, 3055-3074).
- Metadata cache 1 GiB and index cache 6 GiB are PER dataset instance unless a Session is shared; index_cache_size (entries) is deprecated (guide.md:2996-3029).
- Scan memory ≈ 2×io_buffer_size(2 GB default, soft) + batch_size(8192 default)×compute_threads; IO pool 64 threads cloud / 8 local; compute pool = host cores (guide.md:2965-3053).
- Fragment hard ceiling 1 TB, reasonable 10-100 GB; S3 object cap 5 TB (guide.md:3103-3111).
- cleanup_old_versions: guide says 7-day default, installed pylance 10.0.0 substitutes 14 days; timedelta(0) collapses to None at the binding; unverified files younger than 7 days are kept unless delete_unverified=True, which is unsafe with any live writer (guide.md:3688-3736; site-packages/lance/dataset.py:2899-2921 per section read).
- merge_insert: multiple matches are UNDEFINED (currently duplicates); rows are re-appended at the end; default 30s timeout applies after the first attempt; use_index helps only if an index exists (lance_sdk.md:2905-2968).
- create_index replace defaults True; FTS covers ONE field, with_position=False by default so phrase queries raise, native FTS only for nearest_to_text (lance_sdk.md:3973-3976, 4563-4616, 5375-5382).
- Query distance_type must equal the trained metric; ANN/KNN need a limit; plain queries have NO default limit (lance_sdk.md:5488, 5305, 5363, 6042).
- lance-ray: exactly one of uri or namespace+table_id; read/write/add_columns take a namespace INSTANCE, index/compaction/search take namespace_impl + namespace_properties; scalar distributed types INVERTED/FTS/BTREE/BITMAP only; vector IVF_FLAT/IVF_SQ/IVF_PQ only; num_workers clamped to fragment count (ray.md:44-50, 156-158, 185, 255-259, 593-595).
- Spec wire shape for DescribeTable: only with_table_uri, load_detailed_metadata, check_declared are query params; version, tag, branch, vend_credentials are in the REQUIRED JSON body (spec.yaml:395-417, 2786-2830; rest/index.md 'DescribeTable').
- Partitioned namespaces: Lance has no native partitioning; a Partitioned Namespace is a Directory Catalog whose __manifest metadata carries partition_spec_v<N>; multi-partition writes are not atomic unless read pointers are updated in ONE __manifest commit with rebase-or-fail (namespace.md:197-211, 487-530). rask's MAX_NAMESPACE_DEPTH=8 (identifiers.py:45-66) would bound the vN + per-field + dataset nesting (arithmetic only, unconfirmed).
- A second lance.tracing.capture_trace_events call in one process panics and poisons the tracing mutex; index_stats on a JSON index panics (todo!()) — both are pyo3 PanicException (BaseException) (lance_trace.py:31-39; index_health.py:65-80, 115-127).

### 9.2 The GET drift, resolved

Section 3 blocker B3 blamed "spec-revision drift". The sources say otherwise: the spec and lance-namespace's generated `reqwest` client have said POST for `count_rows` and `tags/list` at every tag since 0.9.0. The GET is in the **lance repository**: pylance's bundled `RestNamespace` (`rust/lance-namespace-impls/src/rest.rs`) uses `get_json` for exactly those two ops at v10.0.0 and at main, and pylance's bundled reference server `RestAdapter` (`rest_adapter.rs`) mounts them as GET too. lance-namespace 0.12.0's `connect("rest", …)` resolves to that pylance class (`NATIVE_IMPLS["rest"] = "lance.namespace.RestNamespace"`), so every Python user of the "rest" alias inherits the GET. rask should dual-mount (already the B3 fix) and file the one-line upstream fix.

Two related facts from the same file: the bundled client maps connection properties `header.*` **and** `headers.*` to request headers (rest.rs:277-281), and its dynamic context provider honours only `headers.*` (rest.rs:110-113), while the 0.12.0 spec says `header.`. Response headers are never mapped back into `context` by that client. So "context ↔ header" is unimplemented on both ends today, and rask implementing the response side would be ahead of the reference client.

### 9.4 Branching and shallow clone (post → `format/table/branch_tag.md` + `layout.md`)

Both docs are fully present in the vendored `file_format.md` (zero missing lines), so the digest rules BR13, BR20 and the constraints on names already reflect them. The load-bearing facts, restated because the post is the first place most readers meet them:

- A branch **is** a shallow clone. Its versions, transactions, deletions and indices live under `tree/{branch}/` in the dataset root; its metadata is `_refs/branches/{name}.json` with `parentBranch`, `parentVersion`, `createAt`, `manifestSize`, `metadata`. `/` in a branch name is a real subdirectory under `tree/` and `%2F` in the ref file name.
- A shallow clone's manifest carries `base_paths`: `{id, name?, is_dataset_root, path}` with `path` **absolute**; inherited fragments carry `base_id` pointing at the source; new fragments carry the clone's own base. Only the manifest and new files live in the clone. The source "remains immutable and can be garbage collected independently", which is exactly why a moved or renamed source strands every clone (rask refuses that rename, dataplane.py:401-428).
- Tags are always at the root `_refs/tags/{tag}.json` and record `{branch?, version}`, so one tag namespace spans all branches; tag names cannot contain `/`.
- Portability: a single-base dataset relocates by copying its root; a multi-base one needs only the manifest's `base_paths` rewritten.
- Feature flag 16 (`FLAG_BASE_PATHS`) marks any dataset using this. rask's maintenance whitelists it only for root-scoped operations (`SUPPORTED_FOR_GC`), which is correct: an orphan scan that lists the clone's prefix would report the source's live files as garbage.

### 9.5 Multi-base layout (post → `layout.md` "Base Path System" + `guide/object_store.md`)

The layout half is in the vendored docs (hot/cold tiering, multi-region, shallow clone all resolve through the same `base_id` lookup). What is **new since the vendored copy** is the configuration half in `object_store.md`:

- **Per-base storage options.** A key `base_<id>.<key>` applies `<key>` to the base with that manifest id; every base inherits the unscoped options; exact `base_store_params` (keyed by base URI) take precedence. This is the mechanism the digest's "per-base storage options must be re-supplied on read" deviation was missing. rask passes `base_store_params` on the write path (dataplane.py:241-262) and nothing on the read path; with `base_<id>.` keys the read path can carry per-base credentials without knowing base URIs up front. It is also the format-level answer to "storage profiles per warehouse" (lakehouse §11 E): a warehouse in another bucket or account is a base with its own scoped options.
- **`aws_provider_scheme`** (`token` | `ecs` | `irsa`) pins one dataset to one credential provider so two datasets in one process can use different AWS auth. Not present in pylance 10.0.0 (grep of the installed `dataset.py`); relevant to `vending.py`'s WebIdentity/STS modes once it lands.
- **Server-side copy** is opt-in via `LANCE_IO_SERVER_SIDE_COPY_ENABLED`; deep clone streams through the client with `LANCE_DEEP_CLONE_STREAM_CONCURRENCY` (default 4). rask's sweep does no deep clones today; note for the "clone to another warehouse" case.
- **Stores without reliable put-if-not-exists** (Tencent COS with versioning ever enabled) require a custom `commit_lock`/`CommitHandler` for every writer, and the doc's upgrade guidance is to quiesce all writers before rolling a new Lance version. rask verifies RustFS `If-None-Match` (BR2); this section is the reason that verification must be per store, not assumed.

### 9.6 Blob v2 (post → `guide/blob.md`, 32 lines newer than the vendored copy)

- **Logical shape is now specified.** A blob v2 field is `ARROW:extension:name = "lance.blob.v2"` over a struct in one of two shapes: Minimal `{data: LargeBinary?, uri: Utf8?}` or Complete `{data, uri, position: UInt64?, size: UInt64?}`. Exactly one of `data`/`uri` per non-null row; `position`/`size` both-or-neither; a range requires `uri` and `size > 0`; inline `b""` is the empty blob. Lance preserves the accepted logical shape across create/append/merge-insert, but descriptor scans return the compact stored shape. Blob v2 fields may be **nested** in structs and lists.
- **Placement.** Doc default: inline under 16 KiB, packed `.blob` sidecars in between, dedicated `.blob` file over 2 MiB; `dedicated` is checked first; thresholds persist in the schema and an append naming different values is rejected; `blob_pack_file_size_threshold` (Spark doc: default 1 GiB) rolls sidecar files and does not affect placement. rask measured 64 KiB / 4 MiB on pylance 10.0.0 and pinned those (MM3). The doc and the binary still disagree, so pinning stays the rule.
- **New read API: `read_blob_ranges(column, requests=[(row, offset, length)], selector=ids|addresses|indices)`**, one planned call for many blob-local ranges, present in pylance 10.0.0. Results carry `request_index`, row address, bytes; a null blob yields `None`; an empty range on a non-null blob yields `b""` without I/O; a range past the logical size is an error. The guide now states that `read_blobs`/`take_blobs` **preserve cardinality** (one element per selected row, `None` for null). rask's `blobs.py` documents the pylance-9 "silently dropped" behaviour and the pylance-10 `None` slot, which matches; the `all_binary` scan path rask uses for cardinality is still right for bulk reads.
- **When to use a blob column:** partial/streaming reads, or average payload ≳ 1 MB (compaction re-copies inline payloads into every new version but references `.blob` files). Below a few tens of KB read whole, inline binary is fine. This is MM2 verbatim.
- rask's `/v1/table/{id}/blobs` door (data.py:632) already serves one row's blob as a `StreamingResponse` over `take_blobs` chunks with `Range`, `Content-Range`, `ETag` and `If-Range`. `read_blob_ranges` is the batched, planned alternative for a "many rows, one range each" client (a viewer fetching headers, a training loader reading crops), and is the API a spec client will use against rask's storage directly once credentials are vended.

### 9.7 Late materialization in Spark (post → `lance-spark/docs/src/config.md` and `operations/dml/*.md`)

- Spark reads a blob v2 column as a **descriptor struct** `struct<kind:short, position:long, size:long, blob_id:long, blob_uri:string>`; "descriptor queries do not fetch bytes". Filter pushdown is disabled on blob v2 tables (zonemap fragment pruning still runs).
- Writes go through the catalog path with `file_format_version = 2.2` and `<column>.lance.encoding = blob`; Spark accepts `BINARY` and maps it to the blob write struct at encode time. Copying blobs between tables is a direct column select in `INSERT … SELECT` / CTAS; transformed values, `DISTINCT`, `GROUP BY`, `UNION`, joins of several blob sources keep descriptor semantics and cannot be inserted into a blob column. On Spark 3.5+, `MERGE`/`UPDATE` deep-copy blobs assigned from a source column and carry untouched blobs forward; binary literals are rejected. `ADD COLUMNS … FROM` writes a blob column only if the encoding property was persisted first.
- The lesson for rask: **the descriptor is the late-materialization contract.** A governed table's blob column can be listed, filtered on size/kind/uri, joined and copied without a byte moving, and the bytes are fetched by whichever engine holds credentials, at the row it needs. That is the same posture as rask's `/blobs` door and the annotator's row-wise fetch, and it argues for exposing the descriptor struct (not bytes) on rask's Arrow query responses by default, with `blob_handling="all_binary"` opt-in.

### 9.8 lance-ray 0.5.0: external blobs have a first-class mode

`write_lance(..., external_blob_mode="reference" | "ingest", allow_external_blob_outside_bases=..., initial_bases=[DatasetBasePath...], base_store_params={base_uri: {...}})`. `"reference"` stores the external URI; `"ingest"` reads the external bytes and writes them into Lance-managed storage. pylance 10.0.0's `write_dataset` carries the same `external_blob_mode`. This is the format's own answer to lakehouse-analysis Q4: a governed table may point at archival bytes in place (reference) or take custody of them (ingest), and the choice is a per-write parameter, not a second table kind. rask's ingest already picks reference when an external base is registered and managed otherwise (`ingest/worker.py:212-216`); the platform should name that choice in the produce contract rather than infer it.

### 9.9 The blob-streaming spec (lance.org → `lance-context/docs/src/specs/rollout-blob-streaming.md`)

This is a **lance-context** document (the agent-memory / RL-rollout store built on Lance), not a core-format spec. What it says, and why it matters here:

- lance-context's rollout `binary_payload` is stored as plain inline `LargeBinary`, **not** blob v2, because its read path is the **MemWAL LSM scanner**, which "has no blob-materialization step, so a blob-v2 column reads back as `None` through it". Consequence: every blob is fully resident in RAM at upload and at download (≈2× at the instant of download).
- Implemented mitigations: chunked download bodies (256 KiB frames, refcounted slices of one buffer, `Content-Length` still set); a single-scan record+blob read; and a **process-wide in-flight blob-byte budget** (`ROLLOUT_MAX_INFLIGHT_BLOB_BYTES`): uploads reserve their `Content-Length` before buffering, downloads hold the reservation until the last frame flushes, and an unadmittable request is rejected **503 OVERLOADED** with a counter, rather than allocated. The budget bounds concurrency, not blob size: a lone request larger than the budget is admitted when idle. Sizing guidance: ~1–1.5 GiB on a 4 GiB pod.
- Proposal (not built): blob v2 for the **base table** with `BlobFile` range reads, inline in the WAL tail only, then streamed ingest into the blob column.

Three things carry over to rask:

1. **rask already has the streaming half** (`/blobs` streams `take_blobs` chunks; the viewer's media door uses `take_blobs(..., ids=[rowid])`) and **not the admission half**: no service bounds in-flight blob bytes. Under a burst of large media reads, catalog and viewer pods will OOM before they 503. A `RASK_MAX_INFLIGHT_BLOB_BYTES` budget with a 503 + `Retry-After` on the blob doors is a small, contained change and should be on the list in §8.
2. **MemWAL is a trap for blob columns.** If rask ever adopts MemWAL for high fan-in bronze ingest (the lance-context deployment doc shows the pattern: one shard per stable pod id, no coordinator, PUT-IF-NOT-EXISTS with epoch fencing), governed blob v2 columns will read back `None` through the LSM scanner until upstream fixes it. Document the constraint before anyone reaches for MemWAL.
3. **Server-id sharding is a coordinator-free alternative to the ingest lease** in lakehouse-analysis §3/§11 C. Each replica writes its own shard keyed by `uuid5(instance_id)`; MemWAL's single-writer invariant holds by construction; reads union all shards from object storage, so no read affinity is needed. The trade-off is one flush per append and throughput scaling by adding shards. It applies to append-only landing, not to the anti-join dedup rask's ingest does today.

### 9.10 Feature flags: the whitelist is out of date, safely

`format/table/versioning.md` now lists bits 32 (`FLAG_DISABLE_TRANSACTION_FILE`, writer-only: transactions recorded in the manifest, no `.txn`), 64 (`FLAG_UNSTABLE_DATA_OVERLAY_FILES`, "release builds reject it unless explicitly opted in") and 128 (`FLAG_COVERED_INDEX_METADATA`: an index declares covering columns, so `fields` = keyed columns followed by carried ones; a reader without this flag would pick an index by field membership and answer a query on a carried column with the wrong index). Bits ≥ 256 are unknown. rask's `features.py` whitelists 1|2|4|8 (+16 for root-scoped GC) and names 64 as measured; it does not know 32 or 128, so a dataset carrying either is refused by maintenance with a message naming the bit. That is the intended fail-closed behaviour (BR14), but two comments there are now stale ("the vendored spec table stops at 16") and flag 32 deserves a decision: rask's replay marker and `/history` read `.txn` files (`read_transaction`), which flag 32 moves into the manifest.
