Read step 3–5 carefully: the cascade is driven by the catalog announcing the write, not by the ingest call. That is why an external writer — Spark, Argo, anything — that writes through the catalog's data door drives the cascade identically, with no rask service in the loop on the producing side.

The trap that will catch an integrator

POSTing OpenLineage to /api/lineage — the door whose own docstring advertises “Airflow, Spark, dbt … with no glue” — fires nothing. It records to the graph and returns. The cascade listens to a NATS topic, and nothing republishes from HTTP ingest onto it. You get a perfect lineage graph, zero compute, every pod green. (The docstring now says so; it did not until today.)

4 · What ray_stage_job does — and why this is the most surprising thing here

It is 581 lines. Strip the media branch, the delta branch, the trace plumbing and the contract assertions, and the actual transform is this:

Carry source_rowid forward. Set stage to a constant string. Set lineage to a constant JSON document. Write it back.

That is the whole computation of a generic cascade stage. It reads a Lance dataset, stamps three provenance columns, and writes a Lance dataset. No model, no aggregation, no join, no filter — except in the delta lane, where it adds a version predicate.

The observation worth sitting with

The default cascade runs a distributed Ray Data job to add three constant columns. That is a metadata write, not compute. It is also why the estate already has a second, in-process executor behind a boolean (use_ray) — because for the default lane, distribution buys nothing.

Real compute lives in the sealed runners. Those are where a workload's actual transform — a model, an embedding, a transcription — runs, and they get their own images. The generic stage job is the platform's default transform, and the default is provenance.

Why it is baked into the image

Two reasons, both recorded in the dockerfile:

  • Ray documents runtime_env as development-only. Shipping code or dependencies at replica start is refused by standing ruling — a stack resolved at submit time is not a reproducible build.
  • It was once not baked, and the failure was invisible. Every submitted job died with can't open file '/home/ray/jobs/ray_stage_job.py' and exit code 2, which surfaced as missing data rather than a missing file. The cascade's success path had never once run. A test now reads the entrypoint defaults out of the config and asserts the image bakes each one.

So “baked” is correct. What is not correct is that the catalog knows the baked list — see §2's dotted line.

5 · What a “lane” actually is

You suspected this was doing more than one job. It is doing six — and the estate already knew: commit 5cb121b9 is literally titled “rename the declared LANE to a TRANSFORM, one meaning at a time”, and says “The word carries THREE unrelated meanings in this repo and only one of them is the target.” That rename fixed the governed one and deliberately left the rest.

SenseWhat it means there
The declared recordRenamed away. It is now a TransformSpec. lane survives only as a read-compat alias so pre-rename records still parse — a migration shim, not vocabulary.
A mover DeploymentNever actually called a lane in code — the chart key is name. The word appears only in comments around it. A mover is a (from-ns, to-ns, sub-topic, pub-topic, identity) tuple.
lane_key(project, id)Genuinely named lane, and a misnomer: it strips the tenant prefix, turning acme-bronze$events into bronze$events. It is a de-qualified catalog identifier.
<tier>-<lane> namingA directory suffix (bronze-media). This one causes real bugs — the catalog composes the opposite order (acme-bronze), so a parser reducing from the wrong end returns a tier that does not exist.
“Which code branch ran”Three unrelated uses: lane=full|delta in the job, durable|inline in flows, BUS|FEED in notifications. None relate to the medallion.
A UI stripThe annotator’s text column beside the image. Different domain entirely.
The verdict

“Lane” is not an abstraction — it is residue. Of ~1,350 occurrences, roughly 1,170 are prose. It is overwhelmingly narration, not code. The one governed meaning has already been renamed; what is left should be finished, not designed around.

Topics are shared, not per-edge. Every subscribed mover receives every trigger on its topic and decides by a string comparison on the payload’s dataset field. That in test is the only thing separating pipelines — not a queue, not a namespace, not a Deployment boundary.

The silent failure this creates

Declaring a transform silently changes the ingest head’s behaviour: its from_id becomes a cascade entry point, so arrivals on that table now publish a trigger — even when no mover is bound to that declaration. The trigger goes out, every mover compares the string, they all drop it as “another lane’s”, and the run is over. You get a counter tick and a debug log. Nothing is red.

So a declaration alone does nothing useful, and is not obviously inert. Making it real still needs a chart edit and a helm upgrade — which is precisely the deploy-time step the declared record was invented to escape.

Does it weld ingest, batch and the gate together?

Mostly no, and the parts are more separable than you feared:

  • Ingest works with zero declarations. The head recognises the chart-configured bronze pair directly.
  • The cascade works with zero declarations. Unset, the mover uses its Deployment’s own settings — and no shipped mover row sets one, so declarations are not in use in the deployed estate at all.
  • The gate is keyed by PROJECT, not by pipeline — gate_specs.py says so in capitals. One spec per tenant, resolved on every stage write, falling back to chart settings when absent. That is the opposite policy from a transform, which refuses rather than falls back.

So the welding is not ingest↔batch. It is batch↔gate (§9.4), plus the fact that a hop is a Deployment rather than a declaration (§9.5) — which is the one you have chosen to fix.

10 · What looks wrong

Ranked by how much damage each can do.

1 · The output contract is unwritten — and is already being violated

Twelve obligations a job must satisfy (governance columns, provenance carry-forward, cardinality, stable row ids, delta semantics…) exist only as control flow inside one Python file. The platform verifies three of them after the write. Nothing anywhere asserts a published tier carries stage, lineage, or a non-null source_rowid.

And this is not theoretical: runners/dummy is a declarable, baked, accepted lane whose output has no stage column, no lineage column, an int64 source_rowid where the platform mints uint64, and fabricated parents. Nothing is red.

2 · The governance door knows what Ray is

The allowlist — the literal string /home/ray/jobs/ and three filenames — lives in the shared platform library, and the catalog enforces it when a transform is declared. The word “Ray” is in the catalog’s published OpenAPI and regenerated into the TypeScript client. A Spark lane cannot be declared. Meanwhile the compute zone carries a comment saying “A TRANSFORM IS NOT A RAY JOB” — which the backend falsifies.

3 · The cascade is forward-only and unrepairable

Zero cron reconcilers on the medallion, while five exist elsewhere. The operator surface is list, inspect, terminate — there is no re-run verb. The incremental machinery exists (the delta lane, addressed by Lance version, verified running), but no door triggers it. So when a hop is missed, nothing notices and nothing can re-drive it.

4 · Two quality gates that disagree, one of them dead

MEDALLION_QUALITY_ENABLED exists in code, defaults to false, and renders nowhere in the chart — dead config. Meanwhile the catalog’s publish door asserts unconditionally, with no toggle. So the gate you can configure is off, and the gate you cannot configure is mandatory.

You asked to run batch without a gate. Today you cannot. The honest fix is to split them: row_count_positive and blob_resolves are structural integrity — publishing an empty table or one with dangling blob pointers is a bug, not a policy — so they stay mandatory. not_null on a caller-named column is policy, and that becomes opt-in per declaration.

5 · A hop is a Deployment, not a declaration

Adding a processing step means a new Deployment, two new topics and a chart edit. You have chosen the fix — one generic runner executing N declarations — which is also what makes RayJob CRs and Kueue land naturally.

6 · Kueue is wired and structurally bypassed

The queue templates exist and are gated on a flag. Every job goes through Ray’s Jobs REST API, which creates no custom resource — so Kueue has nothing to admit, queue or preempt. It is not misconfigured; it is unreachable.

7 · Smaller, but real

use_ray is a boolean where an engine selector belongs — the estate already runs two executors and the governed record can only describe one. Ray’s status vocabulary (SUCCEEDED/FAILED/STOPPED) is copied into the workflow body. Three ray_* fields ride the published trigger, which makes the engine’s name part of a wire contract. And ~1,367 orphan rows sit in the workflow state store with no TTL and no alert.

14 · Maintenance on Ray — the correction

You believed compaction, reindex and pruning could be configured to run on lance-ray in the Ray cluster. They cannot, and the reason is worth knowing.

Two facts, both checked

There is no Ray path in services/maintenance at all. No import, no setting, no branch. Compaction, optimize_indices and cleanup_old_versions run in-process on pylance, one ordered pass per dataset, on a cron binding. scripts/ray_lance_job.py is a standalone demo that proves the distributed Lance path works; it is not wired to maintenance and nothing calls it from there.

And the distributed compaction is broken upstream. Measured on lance-ray 0.5.0 + pylance 10.0.0: lance_ray.compact_files reports fragments 4->4 — it does not compact. Native dataset.optimize.compact_files on the identical shape, same options, reduces 4->2. So it is not misuse and it is not Lance. It is pinned with a strict xfail, so the suite will go red the day upstream fixes it.

Is in-process the wrong answer? Not today, and this is the one place the estate is more decoupled than you assumed — maintenance is the most engine-agnostic component in the system. But it will not scale forever: a single pod compacting every dataset in every warehouse is bounded by one process. When it stops keeping up, the fix is to give maintenance the same executor contract the cascade gets — “compact this dataset” becomes a work order any engine can run — rather than importing lance_ray into the sweep. That way the scaling answer and the decoupling answer are the same change.

Why the answer is “stay”

The estate’s orchestration need is unusual, and naming it precisely is what settles the question. It is not “run a DAG on a schedule”. It is:

  • react to data arriving, not to a clock;
  • wait on external compute for hours without holding a queue ack;
  • turn at-least-once delivery into exactly-one submission;
  • hold a 72-hour human approval racing a timer;
  • and do all of it inside a multi-tenant governance model.

That is a workflow engine need, not a data orchestrator need. Dagster, Prefect, Airflow and Metaflow are data orchestrators. Temporal and Dapr Workflow are workflow engines. We are in the right category, running the option that does not require a second control plane.

The honest bottom line

Swapping the orchestrator today would put a better UI on top of the same three problems: the output contract is unwritten, the cascade is not an object, and there is no way to re-drive a hop. Fix those and the tooling question mostly dissolves — and if it does not, Temporal is the answer, not Dagster.

The decisions — settled 2026-08-31

The design session happened, and it was short. All three are answered; none of the work below is waiting on anything.

Decision 1 · Provenance is MANDATORY

Decision 2 · Ray is forever — and the catalog still does not get to know that

Why both packed and dedicated exist: packed stops a million mid-sized images becoming a million S3 objects — listing cost, per-GET overhead, rate limits. Dedicated stops a 100 MB audio file being physically re-copied every time Lance compacts the fragment it shares; a dedicated file is referenced by compaction, not rewritten.

The thresholds are pinned, and the numbers everyone believed were wrong

64 KiB / 4 MiB, fixed in code. The estate previously believed Lance’s defaults were 16 KiB / 2 MiB and therefore believed every scanned page got its own file. Measured on pylance 10: a 20 KB payload landed inline; a 3 MB scanned page landed packed. They are pinned because Lance stores these thresholds in the dataset schema and refuses an append declaring different ones — so a library upgrade that retuned defaults would split an existing table’s writes from its reads with no code change anywhere.

The sidecar, and the 29 MB it nearly deleted

On object storage a table is a directory. The payload bytes sit in a directory named after the data file:

s3://lance-catalog/bronze/pages.lance/
  _versions/*.manifest        ← which files are live
  data/<stem>.lance           ← tabular columns + blob DESCRIPTORS
  data/<stem>/0100….blob      ← THE SIDECAR: the actual bytes
  data/<stem>/1000….blob
Lance’s own API does not name the sidecar

fragment.data_files() returns the .lance file and not the sidecar directory. The orphan scan’s method is “list everything under the prefix, subtract what the manifests reference, report the rest as reclaimable” — so on its first live run it reported 29 MB of real page images as garbage. Fixed by marking each data file’s sidecar directory as referenced too.

One honest residual: a sidecar whose parent data file is referenced by no live version is still reported — and legitimately, because Lance’s own cleanup_old_versions reclaims the .lance and leaves the sidecar behind. That is a real reclamation gap in Lance, named rather than papered over.

Five things that would bite a real million-image run

1 · The embedding is not an embedding. It is 8 floats — the image’s greyscale luminance downsampled to 8 columns, computed by Pillow. Honestly labelled in its own docstring (“no ML-model dependency”), but the silver embedding column has no retrieval value, and nothing else in the estate produces an image embedding.

2 · The media transform is not distributed. It runs on the Ray driver as a plain Python loop, because lance_ray’s write strips blob typing. A million images is one process doing a million decodes and pulling every full-size payload through one pod.

3 · Commit storm. One Lance commit per 128-row batch — roughly 7,800 object-store commits for a single stage over a million rows.

4 · The bytes are copied at every tier on the Ray path. Bronze + silver + gold = three full copies. The in-process executor has a pointer-preserving branch; the Ray path — the default — has none.

5 · The 24-hour watch ceiling. At even 30 ms per image, decode alone plausibly exceeds it, after which the watch stops and the stage never advances even if the job later succeeds.

Cardinality selects no lane at all. It is read once and threaded to a single check that runs after the write. 1:1 additionally asserts the row counts match; 1:N skips that one assertion. Nothing else in the machinery differs.

That asymmetry is a tightening, not a loosening

The check this replaced was a bare rows_out == rows_in on every lane. It forbade fan-out estate-wide, and it was never really about counting — it stood in for “no row lands in a governed tier without a parent”, which counting only approximates. A transform swapping two rows for two unrelated rows passed the old check. So counting was demoted to the lanes that claim it, and the real property was promoted to unconditional.

How provenance survives 1 → 500

All 500 subtitle chunks carry the same source_rowid: the stable row id of the one bronze audio row they descend from — not their immediate parent. That is the join key back to the bytes, and it is why a chunk can always be traced to the audio it came from however many hops later.

But no fan-out transform exists anywhere in the platform

The generic stage job’s only transform is the provenance stamp, which is 1:1 by construction. Declaring 1:N today disables an assertion and produces no extra rows. The capability is declarable, wired end to end from the catalog to the job — and unreachable. Real fan-out has to come from a sealed runner.

Three more that would bite a real transcription lane: (a) an audio bronze can never take the delta lane — the blob test precedes the delta test, so every audio hop full-rescans the whole tier however small the change, and BASE_VERSION is exported, forwarded and then ignored on exactly the lane multimodal data uses; (b) the merge has no delete-by-source clause, so a re-run producing 480 chunks where the last produced 500 leaves 20 orphans that carry a valid parent and therefore pass the contract silently; (c) nothing mints unique child ids — if 500 chunks inherit the parent’s id the merge join is many-to-many, and if they get new ids, no part of the platform generates them.

22 · Could we bootstrap this on another machine today?

You asked. The answer is no, not faithfully — and finding out turned up a security regression waiting to happen.

The Ray head the cascade runs on is not chart-owned

The live head is a hand-applied deploy/ray-lance-demo.yaml, labelled app: ray-lance-head. The chart ships a different thing — a KubeRay RayService — and ray.enabled is true, so a fresh make k3s-up produces a cluster that is not what is running here.

So re-applying it silently undid the work that took the root credential off the Ray plane, and the undo is invisible: the cascade keeps working, because root can do everything the scoped key can. The only way to notice is to read the pod. Fixed — the file now matches the live pod exactly.
