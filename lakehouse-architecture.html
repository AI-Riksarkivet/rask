rask Lakehouse Architecture

What goes in and out of the lakehouse, one real cascade from bronze to gold step by step, how it scores on cloud-native, zero-trust and low-coupling properties, and what it should become using only the stack you have fixed.

What the code supports today

Governed promotion of a table through bronze, silver and gold, with row-level provenance and a publication gate. The stage transforms are generic: they carry rows forward and stamp provenance. They aggregate nothing; the only thing they derive is a thumbnail and an embedding from image blob content (compute.py:1-17).

The default chart cannot run it

ray is on by default and no Ray cluster is rendered, so every stage fails at submit (CP-041). The cascade below uses the make k3s-up profile, which turns the Ray cluster on.

How this was checked

Every step, grade and stack claim was traced in the code at f61dd73 and checked by independent reviewers for accuracy, for Ray and lance-namespace idiom, and for governance and provenance. Anything about the live cluster is not verified.

The in-process lane

With medallion.ray=false, steps 12-16 become one synchronous call inside the stage runner: add columns if the rows line up, otherwise a full-sync merge or a create, then rebuild the lineage index. No workflow, no Ray, no second pass, still the static key (transform.py:849-902; compute.py:311-414).

When the gate holds

Off by default. With review on (by qualityReview or a project's gate record) and a ±25% band breach, the gate holds, emits a FAIL marked HELD, and starts the promotion_review workflow. It asks the configured approver; with no approver set, the review answers BLOCKED. A catalog refusal at publish emits a FAIL marked REFUSED.

Who is told

Each finished or failed run reaches its author (a service), the person who started the cascade, and project watchers, each gated by can_be_notified. A publication notifies nobody. A cascade started with the app token names no person, so its failures reach only service inboxes and project watchers; that is designed, and pinned by a test.

Is the target best practice?

An independent review judged the target against Lakekeeper (the reference CLAUDE.md names) and each product's documented practice: the lance-namespace spec, Kueue's RayJob, RayCluster, persona and admission fair sharing docs, Dapr's NATS and Vault components, fetched on 2026-09-30. NATS JWT, Kyverno, MinIO STS and OpenLineage practice came from the reviewer's knowledge and were not re-fetched. Most of the target is sound. The changes below are recommendations, not rulings; where one changes a row's plan, the row is named.

Sound as designed

  • Machine identity from Kubernetes ServiceAccount tokens (D1).
  • NATS JWT per Dapr app-id: the Dapr NATS component supports jwt and seedKey.
  • The workflow port and outcome door, Dapr Workflow now and Flyte later. Flyte's Ray plugin creates a RayJob, with its own Ray cluster, per task, which Kueue can admit; today's adapter submits to the standing cluster through the Jobs API, which it cannot, so the engine swap would also change how compute is admitted.
  • Kueue, Kyverno and KubeRay installed outside the app release.
  • MinIO AssumeRoleWithWebIdentity as the vend parent, stricter than Lakekeeper's stored static key.
  • Arrival drives the cascade, the catalog assigns locations, and the edge exposes an allowlist of paths.

Missing from the target

rotation of NATS credentials, per-project isolation stated end to end, backpressure, re-drive for the medallion and notifications DLQs (parked, LH-331), an immutable audit store, for example a MinIO object-lock bucket (parked, XC-113), policy-as-code tests beyond FGA and Kyverno.

Gaps outside the counted rows

Each carries its status: a clause in the register, an uncounted parked finding, or behaviour that is deliberate and yours to change.

  • Name a person on service-started cascades. A cascade started with the app token carries no originator, so its failures reach only service inboxes and project watchers (api/produce.py:33,80). This is designed: tests/unit/test_cascade_originator.py pins that a run with no human behind it has no audience. Changing it is your call. deliberate
  • Bracket the Ray stage job's own write. The job emits no lineage. If it fails after committing, report_stage_outcome sends a FAIL with no version (events.py:348-361), so the committed version is recorded only by the reconcile back-fill. CP-029 clause (e)
