# Was the DRY-Ray-wrapper instinct wrong?

## 1. THE VERDICT

**Right about the concerns, right that one kernel should own them, wrong about the vehicle and wrong about the direction.** The kernel is `packages/ray-kit` — already extracted for exactly this (`submit.py:1-26`, R2), already holding the hard parts (deterministic ids with work+code axes, reattach semantics, `trace_env()`, `RayJobError`), and simply under-adopted: it has one consumer, and its own `lineage_env()` at `submit.py:129` has **zero callers repo-wide**. ratch is not the half-built version of that kernel — it is the *pre-ruling* version: its runner-isolation mechanism, `runner_env()` at `core/runners.py:82-105`, builds `runtime_env.pip` from a runner's **unlocked** `[project.dependencies]`, which is precisely what the 2026-08-23 ruling rejected and what the 2026-08-25 baked-image ruling replaced with `runtime_env.image_uri` — so ratch's Ray core should be **retired, not promoted**, and no shared package should ever cross the runner seal.

Which halves win: **Position 1 wins fleet-side** (converge on ray-kit; delete ratch's submitter; unify the credential guard; give `run_runner` an outcome). **Position 2 wins seal-side** (no cross-seal package, no `>=3.10` floor forever, AST pins are the mechanism, de-fuse ratch). Position 1's `packages/ray-contract` loses outright; Position 2's "write more gates *instead of* fixing the fleet-side duplication" loses outright.

## 2. THE LAYER MAP

**Job submission** (id, reattach, terminal policy, auth headers, error taxonomy) → **DRY IN CODE, `ray_kit.submit`.** All three implementations are fleet-side and ≥3.13; no seal is crossed. The cost of not doing it is measured: `2d18976a` added the `work` axis to three files, none under `packages/ratch`, and ratch still seeds `uuid5` on `(runner, token)` alone (`core/jobs.py:132-135`) and returns success on a non-terminal duplicate (`:197-222`) — the exact pre-fix silent-never-ran bug, still live under a docstring claiming parity. Deliberate policy (train's D2 no-resubmit; ratch's resubmit-SUCCEEDED) rides as parameters, not as forks.

**Trace context** → **SPLIT: injection DRY in code, extraction pinned by test.** Injection is already one function (`submit.py:115 trace_env()`) with two callers; that stays. The four inlined `_extract_trace_parent`/`_traced_root` copies **stay inlined and stay pinned** by `tests/unit/test_ray_trace_continuity.py:247`. Position 1's attack on that pin's premise is half-right — `scripts/ray_stage_job.py:65-66` does import `service_kit.lakehouse`, so the head-image scripts are not import-isolated — but `ray_dummy_job` imports `dummy_runner.job` from a sealed runner and cannot be imported by the root suite at all. The pin is ~20 lines, costs nothing, and has already caught real drift (the dummy and lance lanes were running untraced). Not worth a refactor.

**Lineage-completion** → **kernel DRY in code (done); detection LEFT PER-PLANE; the false claim deleted.** The emission kernel is already shared and pinned in three places (`lineage_kit.run_id_for` ≡ `service_kit.openlineage.run_id_for`, `tests/unit/test_events_parity.py:10`). Completion *detection* legitimately differs: medallion has a durable Dapr workflow + bus + reconciler (`workflow.py:32-34,221`); ratch has a person blocking on a terminal. There is no shared contract to extract, because ratch has no consumer of a completion event — and copying medallion's *prose* into that vacuum is literally how ratch-002 happened (`core/jobs.py:156-162`). Two gaps to close: `lineage_env()` gets its caller or gets deleted, and `runners/dummy`'s hand-rolled 161-line emitter gets the pin it lacks.

**Ray Data driving** (driver / registry / stage graph) → **LEAVE PER-PLANE, and retire ratch's.** `core/driver.py` (620 lines) is good code with exactly one consumer: ratch's own CLI. Its isolation lever is `runner_ray_remote_args` → `runner_env()` → `runtime_env.pip` from unlocked deps, defaulted **off** (`RunnersSettings.runner_isolation: bool = False`, `core/runners.py:53`) — which is why the undeclared runner→ratch imports resolve at all: everything shares the driver venv. The production Ray Data lane is `scripts/ray_stage_job.py` plus each sealed runner's own pipeline, under `image_uri` (`chart/templates/rayservice.yaml:43`). This layer is superseded, not unfinished.

**Serve + actor patterns** → **PIN BY TEST, all nine runners, zero dependency cost.** The version wall is decisive and permanent: ratch and ray-kit are `>=3.13`; `insid3` is `==3.10.*`; `asr`, `diarize`, `voiceprint`, `topics`, `kg` are `>=3.10,<3.13`. **Six of nine runner environments cannot install any platform package**, before a single torch pin is considered — and `htr` pins `ray[...]>=2.58,<2.59`, so a shared package would inherit one workload's ceiling as the platform's. Only `assist`, `dummy`, `htr` even ship a `uv.lock`, so only those three are bakeable at all. A shared kit reaches at most three; `test_serve_deployments_do_not_block_the_loop.py` reaches nine today. The missing gate is the knobs: `RASK_SERVE_REPLICAS`/`GPU_FRAC` read three times with 2/0.49 (htr), 1/0 (voiceprint), hardcoded 1 (topics), pinned by nothing.

**Env + secrets forwarding** → **DRY IN CODE fleet-side, plus one cross-plane root-suite pin.** This is the layer that has already cost real money twice, and the two fixes are not equivalent. Medallion omits the secret from the env dict and sources it from the pod (`91d2e50d`); ratch filters by name shape (`9205f783`, `core/jobs.py:65`: `("SECRET","TOKEN","PASSWORD","CREDENTIAL")` over a wildcard `MEDIA_`/`AWS_` forward). A `MEDIA_API_KEY` or `MEDIA_..._PAT` walks straight through ratch's filter into an env the Jobs API echoes; medallion's mechanism cannot have that hole. Each is pinned only by its own plane's test — no cross-plane pin exists. Severity is honest: in-cluster the Ray pods carry no `AWS_*`, so the exposure is dev-machine/CI-scoped. It is still the one thing the estate's gate-based regime lost outright. The `RASK_PARAM_` platform/workload split (`ray_submit.py:198-207`) belongs in the same kernel; ratch has no equivalent.

## 4. WHAT NOT TO DO

- **Do not promote ratch to the platform's Ray kernel.** Three things fused; an institution's URL and Swedish prompts inside `packages/`; a dep surface (`pylance`, `lancedb`, `lance-ray`, `typer`, `pillow`, `ray[data,default,serve]`) that a kernel must not carry; and a runner-isolation mechanism the owner's own 2026-08-25 ruling replaced.
- **Do not build `packages/ray-contract` or any cross-seal "runner-kit."** It would have to hold `requires-python >=3.10` **forever**, and it would reach three of nine runners on day one (locks exist for `assist`, `dummy`, `htr` only) against AST gates that reach nine today at zero dependency cost. Torch is pinned five ways; `htr` pins ray `<2.59`. One workload's ceiling becoming the platform's is the exact inversion the seal exists to prevent.
- **Do not legalize the current imports by making runners declare ratch.** Same wall, plus it puts lance/lancedb/typer/pillow into `asr`'s cu128 environment to obtain a one-line pyarrow helper.
- **Do not de-inline the trace extract or retire its four-way pin.** The "artefact must not import the fleet" premise is only half true, but `ray_dummy_job` genuinely cannot be imported by the root suite, the pin is nearly free, and it has already caught a lane running untraced.
- **Do not build a shared completion contract over medallion and ratch.** One plane has a durable orchestrator, a bus and a reconciler; the other has a shell. That false abstraction is not hypothetical — it is ratch-002.
- **Do not parametrise the deliberate divergences away.** Train's D2 no-resubmit, ratch's resubmit-SUCCEEDED, sync SDK vs async httpx, and the two error tuples are documented and correct. If the kernel's policy parameters pass about three, two honest implementations beat one shared one.
- **Do not answer this with gates alone.** Pin-by-test only binds an invariant someone already thought to write down, and it demonstrably failed at the one security-grade case: the credential fix had to be found and made twice, by two mechanisms, and *the divergence is still unnoticed by any test today.* Gates are right across the seal; inside the fleet, where one lock and one interpreter make sharing cheap, they are the wrong instrument.
- **Do not start with the big ratch split.** Moves 1–7 are cheap, independent, and buy nearly all the correctness. The de-fusion has product surface attached and will stall them if sequenced first.
